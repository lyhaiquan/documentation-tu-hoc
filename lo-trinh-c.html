A1 Biên dịch và chạy chương trình đầu tiên 1 giờ›

Mục tiêu. Gõ được một chương trình, biên dịch, chạy, và hiểu mỗi bước làm gì.

Khái niệm

C là ngôn ngữ biên dịch trước, chạy sau. Không có máy ảo như Java. Mã nguồn .c đi qua bốn bước: tiền xử lý, biên dịch, hợp dịch, liên kết — ra một file thực thi chạy thẳng trên hệ điều hành.

main trả về int: 0 nghĩa là thành công, khác 0 là lỗi. Hệ điều hành đọc con số này.

/* xinchao.c */
#include <stdio.h>      // khai báo printf, không phải "nhập thư viện"

int main(void)
{
    printf("Xin chao\n");
    return 0;              // 0 = chạy tốt
}
gcc -Wall -g xinchao.c -o xinchao
./xinchao
echo $?                    # in ra mã thoát: 0
Bẫy. #include không giống import của Java. Nó chỉ dán nội dung file header vào — tức là dán các khai báo hàm. Mã thật của printf nằm trong thư viện C, được ghép vào ở bước liên kết. Đây là lý do có lỗi "undefined reference" dù đã #include đúng.
Bài tập
  1. In ra tên bạn và năm sinh trên hai dòng.
  2. Bỏ dòng #include <stdio.h> rồi biên dịch. Đọc kỹ cảnh báo gcc đưa ra và giải thích nó nói gì.
  3. Đổi return 0 thành return 3, chạy rồi kiểm tra echo $?.

A2 Kiểu dữ liệu, biến, và sizeof 2 giờ›

Mục tiêu. Biết mỗi kiểu chiếm bao nhiêu byte và vì sao điều đó quan trọng.

Khái niệm

Khác Java, kích thước kiểu trong C không cố định theo chuẩn, chỉ có ràng buộc tối thiểu. Trên máy 64 bit thông thường: char 1 byte, short 2, int 4, long 8 trên Linux nhưng 4 trên Windows. Vì thế mọi code mạng đều dùng kiểu có kích thước cố định.

sizeof là toán tử, không phải hàm, và tính lúc biên dịch.

#include <stdio.h>

int main(void)
{
    char  c = 'A';
    int   i = 42;
    long  l = 42L;
    double d = 3.14;

    printf("char=%zu int=%zu long=%zu double=%zu\n",
           sizeof(c), sizeof(i), sizeof(l), sizeof(d));
    printf("c duoi dang so = %d\n", c);   // 65 — char LÀ số
    return 0;
}
Bẫy. char trong C là số nguyên 1 byte, không phải ký tự Unicode như Java. 'A' chính là 65. Và char có dấu hay không dấu là tùy trình biên dịch — khi đọc byte từ mạng luôn dùng unsigned char.
Bài tập
  1. In kích thước của tất cả kiểu cơ bản trên máy bạn, kể cả con trỏ sizeof(int *).
  2. Gán char c = 200; rồi in bằng %d. Giải thích kết quả.
  3. Cho int i = 3, j = 2; — in i / j. Vì sao ra 1? Sửa thế nào để ra 1.5?

A3 printf, scanf và chuỗi định dạng 2 giờ›

Mục tiêu. Nhập xuất thành thạo, và hiểu vì sao sai chuỗi định dạng lại nguy hiểm.

Khái niệm

printf nhận số tham số tùy ý. Nó không biết bạn truyền kiểu gì — nó tin vào chuỗi định dạng. Sai một ký tự là đọc nhầm vùng nhớ.

int   n = 42;
char  s[] = "chuoi";
double x = 2.5;

printf("%d\n", n);        // int
printf("%s\n", s);        // chuỗi
printf("%f  %.2f\n", x, x);
printf("%c\n", s[0]);     // một ký tự
printf("%p\n", (void *)s);// địa chỉ
printf("%5d|%-5d|\n", n, n);  // canh phải / canh trái

// scanf CẦN dấu & vì phải sửa biến của bạn — xem B4
int tuoi;
scanf("%d", &tuoi);
Bẫy. printf("%d", x) với x là double không báo lỗi lúc chạy, chỉ in ra số rác. Luôn bật gcc -Wall — nó bắt được lỗi này lúc biên dịch. Và không bao giờ viết printf(bien_chuoi); phải là printf("%s", bien_chuoi), nếu không là lỗ hổng format string.
Bài tập
  1. Viết chương trình hỏi tên và tuổi rồi in ra một câu chào.
  2. Cố tình dùng %d để in một double, biên dịch có và không có -Wall, so sánh.
  3. In một bảng 3 cột thẳng hàng bằng %-10s%5d%8.2f.

A4 Toán tử, ép kiểu, tràn số 2 giờ›

Mục tiêu. Đoán đúng kết quả của biểu thức trộn kiểu.

Khái niệm

C tự động nâng kiểu trong biểu thức: kiểu nhỏ nâng lên kiểu lớn. Nhưng phép chia hai số nguyên vẫn là chia nguyên, cắt phần thập phân, ngay cả khi gán vào double.

int a = 7, b = 2;
double d1 = a / b;          // 3.0  — chia nguyên TRƯỚC rồi mới gán
double d2 = (double)a / b;  // 3.5  — ép một vế là đủ

unsigned int u = 0;
u = u - 1;                  // 4294967295, KHÔNG phải -1

int big = 2147483647;
big = big + 1;              // tràn số có dấu = hành vi không xác định
Bẫy. So sánh giữa số có dấu và không dấu là nguồn lỗi kinh điển trong code mạng: if (len < sizeof(buf)) với len là int âm sẽ cho kết quả đúng một cách bất ngờ, vì sizeof trả về kiểu không dấu nên len bị chuyển thành số dương khổng lồ.
Bài tập
  1. Đoán rồi kiểm chứng: printf("%d\n", 5 / 2 * 2);
  2. Viết chương trình đổi độ C sang độ F, chú ý không để dính chia nguyên.
  3. Cho int n = -1; unsigned u = 1; — in kết quả của n < u. Giải thích.

C Primer Plus — Chương 5

A5 Rẽ nhánh và vòng lặp 2 giờ›

Mục tiêu. Viết được vòng lặp đọc dữ liệu tới khi hết — khuôn mẫu dùng suốt trong code mạng.

Khái niệm

C không có kiểu boolean theo nghĩa Java. Số 0 là sai, mọi giá trị khác là đúng. Vì thế con trỏ, số nguyên, ký tự đều đặt thẳng vào if được.

int c;
/* Khuôn mẫu đọc tới hết đầu vào.
   getchar() trả về int chứ không phải char, để chứa được EOF (-1). */
while ((c = getchar()) != EOF) {
    putchar(c);
}

/* Vòng lặp vô tận của server — bạn sẽ gặp lại ở F2 */
for (;;) {
    /* accept, xử lý, đóng */
    break;   // tạm thời
}
Bẫy. if (x = 5) — một dấu bằng — là phép gán, luôn đúng, và C không báo lỗi. Java bắt được vì if đòi boolean; C thì không. Bật -Wall để gcc cảnh báo.
Bài tập
  1. Đếm số ký tự, số dòng, số từ trong đầu vào — bài wc kinh điển.
  2. In bảng cửu chương bằng hai vòng lặp lồng nhau.
  3. Viết vòng lặp đọc số tới khi người dùng nhập 0 thì dừng, rồi in tổng.

A6 Hàm, nguyên mẫu, truyền theo giá trị 2 giờ›

Mục tiêu. Hiểu vì sao hàm C không thể đổi biến của người gọi — đây là lý do con trỏ tồn tại.

Khái niệm

C truyền tham số theo giá trị, luôn luôn. Hàm nhận một bản sao. Sửa bản sao thì bên ngoài không biết gì. Đây là nền tảng để hiểu đơn vị B4.

Nguyên mẫu hàm phải khai trước khi dùng, thường đặt trong file header.

#include <stdio.h>

int cong(int a, int b);        // nguyên mẫu
void thu_doi(int x);

int main(void)
{
    int n = 10;
    printf("%d\n", cong(2, 3));

    thu_doi(n);
    printf("n van la %d\n", n);   // vẫn 10!
    return 0;
}

int cong(int a, int b) { return a + b; }

void thu_doi(int x) { x = 999; }  // chỉ đổi bản sao
Bẫy. Quên nguyên mẫu thì trình biên dịch cũ tự đoán hàm trả về int, sinh lỗi rất khó tìm. Luôn khai nguyên mẫu, và luôn ghi void khi hàm không nhận tham số: int main(void) chứ không phải int main().
Bài tập
  1. Viết hàm tính giai thừa, gọi từ main.
  2. Viết hàm doi_cho(int a, int b) cố hoán đổi hai số. Chứng minh nó không hoạt động. Giữ lại bài này, đơn vị B4 sẽ sửa nó.
  3. Tách chương trình thành hai file: main.c và toan.c, biên dịch bằng gcc main.c toan.c -o ct.

C Primer Plus — Chương 9

A7 Chuyển kiểu ngầm định — chỗ đứt giữa A2 và A4 3 giờ›

Mục tiêu. Biết chính xác chuyện gì xảy ra khi bạn trộn int với unsigned, hoặc char với int. Đây là nguồn lỗi im lặng lớn nhất của C.

Vì sao đơn vị này tồn tại

A2 dạy bạn các kiểu. A4 dạy bạn các toán tử. Nhưng khi hai toán hạng khác kiểu, trình biên dịch tự đổi một bên trước khi tính — và nó không hỏi ý bạn, không cảnh báo. Java cũng có chuyển kiểu nhưng chặt hơn nhiều; C thì cho qua hầu hết mọi thứ.

Khái niệm — hai luật

Luật 1 — thăng cấp số nguyên (integer promotion). Mọi kiểu nhỏ hơn int (char, short, _Bool, trường bit) được đổi thành int trước khi tham gia bất kỳ phép tính nào. Không có phép cộng hai char trong C — luôn là cộng hai int.

Luật 2 — chuyển đổi số học thông thường. Sau khi thăng cấp, nếu hai bên vẫn khác nhau thì:

  1. Có double → bên kia thành double
  2. Cùng kích thước, một bên không dấu → bên có dấu bị đổi thành không dấu
  3. Bên không dấu nhỏ hơn → được nới lên kiểu có dấu lớn hơn

Dòng số 2 là dòng giết người.

#include <stdio.h>
#include <string.h>

int main(void)
{
    int      a = -1;
    unsigned b =  1;

    // -1 đổi thành unsigned = 4294967295, nên -1 > 1 là ĐÚNG
    printf("(-1 > 1u) = %d\n", a > b);          // in ra 1

    char s[] = "";
    // strlen trả về size_t (không dấu). 0 - 1 = 4294967295, không phải -1.
    printf("strlen-1 = %zu\n", strlen(s) - 1);

    if (strlen(s) - 1 >= 0)
        printf("dieu kien nay LUON dung\n");     // vòng lặp vô hạn ở đây

    char c = 200;                                 // char có dấu trên x86
    printf("c = %d\n", c);                        // in ra -56, không phải 200
    return 0;
}
Ba chỗ luật này cắn bạn trong code mạng
  • read() trả về ssize_t (có dấu). Nếu bạn hứng vào size_t n thì lỗi -1 biến thành một số cực lớn, và n > 0 trở thành đúng — bạn xử lý 18 tỉ byte rác.
  • Đọc byte từ mạng vào char rồi so với 0xFF: byte 0xFF thành -1, không bao giờ bằng 255. Byte dữ liệu thô phải dùng unsigned char.
  • Tính độ dài còn lại: buf_len - da_doc với cả hai là size_t, nếu da_doc lớn hơn thì kết quả không âm mà là số khổng lồ → tràn bộ đệm.
Bẫy. char có dấu hay không do trình biên dịch quyết: x86 Linux là có dấu, ARM là không dấu. Cùng một code, chạy trên máy tính và trên Raspberry Pi cho kết quả khác nhau. Muốn chắc thì viết rõ signed char hoặc unsigned char.
Bài tập
  1. Chạy ví dụ trên. Giải thích bằng lời vì sao -1 > 1u ra đúng.
  2. Viết vòng lặp for (size_t i = n - 1; i >= 0; i--) duyệt ngược mảng. Nó chạy mãi không dừng. Sửa hai cách: đổi kiểu i, và giữ size_t nhưng đổi điều kiện.
  3. Biên dịch lại toàn bộ ví dụ với gcc -Wall -Wextra -Wsign-compare. Ghi lại cảnh báo nào bắt được lỗi nào. Từ nay luôn bật ba cờ đó.

Đây là phần quyết định. Ai bỏ cuộc với C đều bỏ ở đây. Đi chậm, vẽ hình ra giấy, đừng vội sang phần sau.

B1 Bộ nhớ là gì, địa chỉ là gì 2 giờ›

Mục tiêu. Hình dung được bộ nhớ như một dãy ô đánh số, và biến nằm ở đâu trong dãy đó.

Khái niệm

Bộ nhớ là một dãy byte liên tiếp, mỗi byte có một địa chỉ là số nguyên. Khai báo int n; nghĩa là xin 4 byte liên tiếp và đặt tên n cho chúng. Toán tử & cho biết địa chỉ đó.

#include <stdio.h>

int main(void)
{
    int  a = 10;
    int  b = 20;
    char c = 'X';

    printf("a = %d, nam o dia chi %p\n", a, (void *)&a);
    printf("b = %d, nam o dia chi %p\n", b, (void *)&b);
    printf("c = %c, nam o dia chi %p\n", c, (void *)&c);
    printf("a chiem %zu byte\n", sizeof(a));
    return 0;
}

Chạy vài lần và để ý: địa chỉ đổi mỗi lần chạy (do hệ điều hành ngẫu nhiên hóa), nhưng khoảng cách giữa &a và &b thì ổn định.

Bẫy. In địa chỉ phải dùng %p và ép sang (void *). Dùng %d để in địa chỉ là sai kiểu, trên máy 64 bit sẽ in ra số cụt.
Bài tập
  1. Khai báo một mảng int arr[5], in địa chỉ từng phần tử. Khoảng cách giữa hai phần tử liền nhau là bao nhiêu? Vì sao?
  2. Làm lại với char arr[5] và so sánh.
  3. Vẽ ra giấy sơ đồ bộ nhớ của chương trình ví dụ trên.

B2 Con trỏ: khai báo, gán, lấy giá trị 3 giờ›

Mục tiêu. Đọc trôi chảy int *p = &a; và *p = 5; mà không phải nghĩ.

Khái niệm

Con trỏ là một biến chứa địa chỉ. Hai toán tử ngược nhau:

  • &x — lấy địa chỉ của x
  • *p — giá trị nằm tại địa chỉ p

Dấu * có hai nghĩa khác nhau tùy chỗ: lúc khai báo nó nói "đây là con trỏ", lúc dùng nó nói "lấy giá trị tại đó".

#include <stdio.h>

int main(void)
{
    int a = 10;
    int *p;          // p là con trỏ tới int (chưa trỏ đâu cả)

    p = &a;          // giờ p chứa địa chỉ của a

    printf("a  = %d\n", a);      // 10
    printf("*p = %d\n", *p);     // 10 — cùng một ô nhớ
    printf("p  = %p\n", (void *)p);
    printf("&a = %p\n", (void *)&a);   // hai dòng này giống nhau

    *p = 99;                     // ghi qua con trỏ
    printf("a gio la %d\n", a);  // 99 — a đã đổi!
    return 0;
}
Bẫy. Con trỏ chưa gán trỏ vào chỗ ngẫu nhiên. Viết int *p; *p = 5; là ghi vào một địa chỉ vô nghĩa — chương trình sập hoặc, tệ hơn, không sập mà phá dữ liệu khác. Luôn khởi tạo: int *p = NULL;
Bài tập
  1. Khai báo hai biến, hai con trỏ, cho chúng trỏ chéo nhau rồi in ra để kiểm chứng.
  2. Viết int **pp = &p; và in **pp. Vẽ sơ đồ ba ô nhớ nối nhau.
  3. Thử int *p = NULL; printf("%d", *p); — quan sát chương trình sập, và nhớ thông báo lỗi đó.

B3 Con trỏ và mảng, số học con trỏ 3 giờ›

Mục tiêu. Hiểu vì sao arr[i] và *(arr + i) là một.

Khái niệm

Tên mảng, khi dùng trong biểu thức, tự chuyển thành địa chỉ phần tử đầu. Cộng 1 vào con trỏ không cộng 1 byte mà cộng một phần tử — trình biên dịch tự nhân với sizeof kiểu.

#include <stdio.h>

int main(void)
{
    int arr[5] = {10, 20, 30, 40, 50};
    int *p = arr;            // không cần &, tên mảng đã là địa chỉ

    printf("%d %d\n", arr[2], *(arr + 2));  // 30 30 — như nhau
    printf("%d %d\n", p[2],   *(p + 2));    // 30 30

    // duyệt bằng con trỏ
    for (int i = 0; i < 5; i++)
        printf("%d ", *(p + i));
    printf("\n");

    printf("sizeof(arr) = %zu\n", sizeof(arr));  // 20 — cả mảng
    printf("sizeof(p)   = %zu\n", sizeof(p));    // 8  — chỉ con trỏ
    return 0;
}
Bẫy. Khi truyền mảng vào hàm, nó suy biến thành con trỏ và mất thông tin kích thước. Bên trong hàm, sizeof(arr) trả về kích thước con trỏ chứ không phải mảng. Vì thế mọi hàm C nhận mảng đều phải kèm thêm tham số độ dài — chính là lý do read(fd, buf, len) có tham số len.
Bài tập
  1. Viết hàm int tong(int *a, int n) tính tổng mảng.
  2. In arr, &arr[0], p, p + 1 — giải thích khoảng cách giữa p và p + 1.
  3. Viết hàm đảo ngược mảng tại chỗ, dùng hai con trỏ chạy từ hai đầu vào giữa.

B4 Con trỏ làm tham số — sửa biến của người gọi 2 giờ›

Mục tiêu. Sửa được bài hoán đổi ở A6, và hiểu tham số kiểu "giá trị-kết quả" mà API socket dùng.

Khái niệm

B5 Chuỗi C và tràn bộ đệm 3 giờ›

Mục tiêu. Xử lý chuỗi an toàn — kỹ năng sống còn khi nhận dữ liệu từ mạng.

Khái niệm

C không có kiểu chuỗi. Chuỗi chỉ là mảng char kết thúc bằng byte 0 ('\0'). Mọi hàm chuỗi đều dựa vào byte kết thúc đó. Thiếu nó là hàm chạy quá vùng nhớ.

#include <stdio.h>
#include <string.h>

int main(void)
{

Mẹo đọc: const gắn vào thứ nằm bên trái nó; nếu bên trái trống thì gắn vào thứ bên phải.

Trình biên dịch giả định: nếu không ai trong chương trình ghi vào biến, giá trị không đổi, nên nó giữ biến trong thanh ghi và bỏ hẳn lần đọc bộ nhớ sau. volatile nói: giá trị này có thể đổi sau lưng anh, đọc lại từ bộ nhớ mỗi lần. Ba trường hợp cần:

  • Thanh ghi phần cứng ánh xạ vào bộ nhớ — chính là code ESP32 bạn viết ở bài IoT. Đọc cùng một địa chỉ hai lần cho hai giá trị khác nhau vì cảm biến vừa đổi.
  • Biến bị hàm xử lý tín hiệu sửa — sẽ gặp lại ở H3, kiểu bắt buộc là volatile sig_atomic_t.
  • Bộ nhớ dùng chung giữa các luồng — nhưng ở đây volatile là không đủ, phải dùng mutex hoặc atomic. Xem H4.

while (dang_chay) { phuc_vu_mot_client(); }

C2 malloc, free, và bốn lỗi bộ nhớ 3 giờ›

Mục tiêu. Cấp phát và giải phóng đúng, nhận diện được bốn loại lỗi bộ nhớ.

Khái niệm

malloc(n) xin n byte, trả về void * hoặc NULL nếu thất bại. free(p) trả lại. Mỗi malloc phải có đúng một free.

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int n = 5;
    int *a = malloc(n * sizeof(int));   // KHÔNG cần ép kiểu trong C
    if (a == NULL) {                    // LUÔN kiểm tra
        fprintf(stderr, "het bo nho\n");
        return 1;
    }

    for (int i = 0; i < n; i++) a[i] = i * i;
    for (int i = 0; i < n; i++) printf("%d ", a[i]);
    printf("\n");

    free(a);
    a = NULL;      // gán NULL sau khi free, tránh dùng nhầm
    return 0;
}
Bốn lỗi phải thuộc tên
  • Rò rỉ bộ nhớ — xin mà không trả. Server chạy vài ngày rồi hết RAM.
  • Dùng sau khi giải phóng — free(p) rồi vẫn đọc *p.
  • Giải phóng hai lần — free cùng con trỏ hai lượt.
  • Ghi quá vùng — xin 5 phần tử mà ghi phần tử thứ 6.
Bẫy. malloc không xóa vùng nhớ; nội dung là rác của chương trình trước. Cần vùng sạch thì dùng calloc(n, size).
Bài tập

C4 realloc và bộ đệm tự lớn 3 giờ›

Mục tiêu. Viết được một bộ đệm tự nới — thứ mà mọi trình phân tích giao thức đều cần, vì bạn không biết trước client sẽ gửi bao nhiêu byte.

Vì sao đơn vị này tồn tại

C2 dạy malloc/free với kích thước biết trước. Nhưng khi đọc từ socket bạn không biết trước độ dài. Java có ByteArrayOutputStream lo hộ; C thì bạn tự viết. Bỏ qua đơn vị này là tới J3 sẽ tắc.

Khái niệm

realloc(p, n) làm ba việc: xin vùng mới n byte, chép nội dung cũ sang, giải phóng vùng cũ. Nó có thể trả về địa chỉ khác — nên mọi con trỏ đang trỏ vào vùng cũ lập tức thành con trỏ treo.

// SAI — mất luôn vùng nhớ cũ nếu realloc thất bại
p = realloc(p, n);              // realloc trả NULL -> p = NULL, rò rỉ

// ĐÚNG — giữ bản sao cho tới khi chắc chắn thành công
char *tam = realloc(p, n);
if (tam == NULL) { /* p vẫn còn nguyên, xử lý lỗi */ return -1; }
p = tam;

#include <stdlib.h>
#include <string.h>

struct dem {
    char  *data;

    size_t cap;    // số byte đã xin
};

int them(struct dem *b, const char *src, size_t n)
{
    if (b->len + n > b->cap) {
        size_t cap_moi = b->cap ? b->cap : 64;
        while (cap_moi < b->len + n)
            cap_moi *= 2;                 // nhân đôi, không cộng thêm 1

        char *tam = realloc(b->data, cap_moi);
        if (!tam) return -1;
        b->data = tam;
        b->cap  = cap_moi;
    }
    memcpy(b->data + b->len, src, n);
    b->len += n;
    return 0;
}

void giai_phong(struct dem *b)
{
    free(b->data);
    b->data = NULL; b->len = b->cap = 0;
}
Vì sao nhân đôi chứ không cộng thêm

Cộng thêm cố định: thêm n byte tốn n² lần chép — thêm 1 MB từng byte một là hàng nghìn tỉ thao tác. Nhân đôi: tổng chi phí chép chỉ khoảng 2n, tức trung bình mỗi byte tốn hằng số. Đây gọi là chi phí khấu hao, và là lý do ArrayList của Java cũng nhân đôi.

Bẫy. Sau realloc, mọi con trỏ cũ trỏ vào vùng đó đều hỏng. Nếu bạn từng lưu char *dau_dong = b.data + 10; trước đó, sau them() nó có thể trỏ vào vùng đã giải phóng. Luôn lưu khoảng cách (size_t vi_tri = 10;) chứ đừng lưu con trỏ.
Bài tập
  1. Cài đủ struct dem ở trên, ghép 100 000 lần chuỗi "abc", in len và cap cuối cùng. Kiểm bằng valgrind --leak-check=full (hoặc gcc -fsanitize=address).

D4 Cấu trúc tự tham chiếu — danh sách liên kết 3 giờ›

Mục tiêu. Ghép con trỏ và struct lại — bài kiểm tra tổng hợp của giai đoạn B, C, D.

Khái niệm

Một struct chứa con trỏ tới chính kiểu của nó. Đây là nền của mọi cấu trúc dữ liệu động, và server thật dùng nó để giữ danh sách client đang kết nối.

#include <stdio.h>
#include <stdlib.h>

struct nut {
    int          gia_tri;
    struct nut  *tiep;      // trỏ tới chính kiểu này
};

int main(void)
{
    struct nut *dau = NULL;

    /* thêm 3 nút vào đầu danh sách */
    for (int i = 1; i <= 3; i++) {
        struct nut *moi = malloc(sizeof(struct nut));
        if (!moi) return 1;
        moi->gia_tri = i;
        moi->tiep    = dau;
        dau          = moi;
    }

    for (struct nut *p = dau; p != NULL; p = p->tiep)
        printf("%d ", p->gia_tri);
    printf("\n");

    /* giải phóng — phải giữ con trỏ tiếp trước khi free */
    while (dau) {
        struct nut *tam = dau->tiep;
        free(dau);
        dau = tam;
    }
    return 0;
}
Bẫy. free(dau); dau = dau->tiep; là lỗi dùng sau khi giải phóng — đọc trường của vùng nhớ vừa trả lại. Phải lưu tiep vào biến tạm trước khi free.

D5 Hàm nhận số tham số thay đổi — printf hoạt động thế nào 2 giờ›

Mục tiêu. Hiểu vì sao printf("%d", "abc") biên dịch lọt mà chạy thì sập, và tự viết được hàm ghi nhật ký cho server của mình.

Vì sao đơn vị này tồn tại

Bạn dùng printf từ A3 mà chưa biết nó là loại hàm gì. Nó là hàm biến thiên tham số — kiểu hàm duy nhất trong C mà trình biên dịch không kiểm tra được kiểu tham số. Mọi server thật đều có một hàm log dạng này.

Khái niệm

Ba macro trong <stdarg.h>: va_start mở, va_arg lấy tham số kế tiếp, va_end đóng. Điểm mấu chốt: bạn phải tự nói kiểu cho va_arg, vì trong đống tham số đó không có thông tin kiểu nào cả — chuỗi định dạng "%d %s" chính là cách printf biết phải lấy gì.

#include <stdio.h>
#include <stdarg.h>
#include <time.h>

// Hàm log: thêm giờ vào đầu, rồi chuyển tiếp mọi thứ cho vfprintf.
// Chú ý cờ __attribute__: bảo gcc kiểm tra chuỗi định dạng như printf.
void nhat_ky(const char *fmt, ...)
    __attribute__((format(printf, 1, 2)));

void nhat_ky(const char *fmt, ...)
{
    char gio[16];
    time_t t = time(NULL);
    strftime(gio, sizeof gio, "%H:%M:%S", localtime(&t));
    fprintf(stderr, "[%s] ", gio);

    va_list ap;
    va_start(ap, fmt);      // fmt = tham số cuối cùng CÓ tên
    vfprintf(stderr, fmt, ap);   // bản "v" nhận sẵn va_list
    va_end(ap);

    fputc('\n', stderr);
}

// Tự cộng dồn: tham số đầu nói có bao nhiêu số theo sau
int tong(int n, ...)
{
    va_list ap;
    va_start(ap, n);
    int s = 0;
    for (int i = 0; i < n; i++)
        s += va_arg(ap, int);    // PHẢI tự nói kiểu là int
    va_end(ap);
    return s;
}

int main(void)
{
    nhat_ky("client %s ket noi, cong %d", "127.0.0.1", 5000);
    printf("%d\n", tong(4, 10, 20, 30, 40));   // 100
    return 0;
}
Vì sao printf không an toàn

Không có cách nào để hàm biết bạn truyền vào bao nhiêu tham số và kiểu gì. Nếu chuỗi định dạng nói %d mà bạn đưa con trỏ, va_arg vẫn cứ đọc 4 byte ở chỗ đó và diễn giải thành số nguyên. Nếu định dạng nói %s mà bạn đưa số 42, nó lấy 42 làm địa chỉ và đi đọc — segfault.

Bẫy bảo mật. printf(chuoi_tu_nguoi_dung) là lỗ hổng format string: kẻ tấn công gửi "%x%x%x%s" để đọc trộm ngăn xếp, hoặc %n để ghi vào bộ nhớ. Luôn viết printf("%s", chuoi_tu_nguoi_dung). Đây là lỗi có thật trong nhiều máy chủ đời đầu, và -Wformat-security sẽ bắt được.
Bài tập
  1. Chạy ví dụ. Rồi cố tình viết nhat_ky("so = %d", "chuoi") và biên dịch với -Wall. Nhờ __attribute__((format)) mà gcc bắt được — bỏ dòng attribute đi, biên dịch lại, xem cảnh báo biến mất.
  2. Viết void in_ip(int n, ...) nhận n chuỗi IP và in mỗi cái một dòng kèm số thứ tự.
  3. Đọc man 3 vsnprintf. Viết hàm char *dinh_dang(const char *fmt, ...) trả về chuỗi đã cấp phát bằng malloc — gọi vsnprintf(NULL, 0, ...) để biết cần bao nhiêu byte trước. Cần dùng va_list hai lần, tức phải va_copy. Bài này ghép C2, C4 và D5 lại.

Sáu toán tử: & và, | hoặc, ^ xor, ~ đảo, << dịch trái, >> dịch phải. Hệ thống Unix gói nhiều tùy chọn nhị phân vào một số nguyên gọi là cờ.

#include <stdio.h>

#define DOC   (1 << 0)   // 0001
#define GHI   (1 << 1)   // 0010
#define CHAY  (1 << 2)   // 0100

int main(void)
{
    int quyen = 0;

    quyen |= DOC;              // bật cờ
    quyen |= GHI;

    if (quyen & DOC)  printf("co quyen doc\n");     // kiểm tra
    if (!(quyen & CHAY)) printf("khong duoc chay\n");

    quyen &= ~GHI;             // tắt cờ
    printf("quyen = %d\n", quyen);   // 1
    return 0;
}
Bẫy. Đừng nhầm & với &&, | với ||. Cặp một ký tự làm việc trên từng bit, cặp hai ký tự làm việc trên đúng/sai. Viết nhầm thì chương trình vẫn biên dịch và cho kết quả sai âm thầm.

E2 Kiểu kích thước cố định và thứ tự byte 3 giờ›

Mục tiêu. Hiểu vì sao code mạng luôn gọi htons().

Khái niệm

Vì int không cố định kích thước, giao thức mạng dùng kiểu chính xác: uint8_t, uint16_t, uint32_t trong <stdint.h>. Ngoài ra còn size_t (kích thước, không dấu) và ssize_t (kích thước có dấu, để trả về -1 khi lỗi).

Endianness — thứ tự các byte của một số nhiều byte. x86 dùng little-endian (byte thấp trước), còn mạng quy ước big-endian. Nên mọi số nhiều byte gửi đi đều phải đổi.

#include <stdio.h>
#include <stdint.h>

int main(void)
{
    uint32_t x = 0x01020304;
    unsigned char *b = (unsigned char *)&x;

    printf("byte: %02x %02x %02x %02x\n", b[0], b[1], b[2], b[3]);
    // x86 in ra: 04 03 02 01  -> little-endian
    // mạng cần:  01 02 03 04  -> big-endian

    if (b[0] == 0x04) printf("may nay little-endian\n");
    else              printf("may nay big-endian\n");
    return 0;
}

Trong code mạng: htons = host to network short (16 bit), htonl = host to network long (32 bit), và hai hàm ngược lại ntohs, ntohl.

Mục tiêu. Đọc được signal(SIGINT, xu_ly) và tham số so sánh của qsort.

Khái niệm

Tên hàm cũng là một địa chỉ. Con trỏ hàm cho phép truyền hành vi vào hàm khác — chính là callback. Trong lập trình mạng, bộ xử lý tín hiệu là con trỏ hàm.

#include <stdio.h>
#include <stdlib.h>

int tang_dan(const void *a, const void *b)
{
    int x = *(const int *)a;
    int y = *(const int *)b;
    return (x > y) - (x < y);
}

int main(void)
{
    int arr[5] = {5, 2, 9, 1, 7};
    qsort(arr, 5, sizeof(int), tang_dan);   // truyền tên hàm

    for (int i = 0; i < 5; i++) printf("%d ", arr[i]);
    printf("\n");

    int (*ham)(const void *, const void *) = tang_dan;  // biến con trỏ hàm
    printf("%d\n", ham(&arr[0], &arr[1]));
    return 0;
}
Bẫy. Cú pháp khai báo rất khó đọc. int (*p)(int) là con trỏ tới hàm nhận int trả int; còn int *p(int) là hàm trả về con trỏ int. Dấu ngoặc quyết định tất cả. Dùng typedef cho dễ đọc.

E5 File I/O và cách C báo lỗi 3 giờ›

Mục tiêu. Xử lý lỗi đúng phong cách Unix — vì socket dùng y hệt cách này.

Khái niệm

Có hai tầng: FILE * với fopen/fread (thư viện chuẩn C, có bộ đệm) và mô tả file là số nguyên với open/read/write (lời gọi hệ thống). Socket là mô tả file, nên tầng thứ hai mới là thứ bạn cần.

Quy ước Unix: hàm trả về -1 khi lỗi và đặt biến toàn cục errno cho biết lỗi gì.

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>

int main(void)
{
    FILE *f = fopen("khong_co_file_nay.txt", "r");
    if (f == NULL) {
        /* ba cách in lỗi, chọn một */
        perror("fopen");
        fprintf(stderr, "errno = %d: %s\n", errno, strerror(errno));
        return 1;
    }

    char dong[256];
    while (fgets(dong, sizeof(dong), f) != NULL)
        fputs(dong, stdout);

    fclose(f);
    return 0;
}

Bản dùng mô tả file, gần với socket hơn:

#include <fcntl.h>
#include <unistd.h>

int fd = open("a.txt", O_RDONLY);
if (fd == -1) { perror("open"); return 1; }

char buf[1024];
ssize_t n;
while ((n = read(fd, buf, sizeof(buf))) > 0)
    write(STDOUT_FILENO, buf, n);   // ghi đúng n byte, không phải sizeof

if (n == -1) perror("read");
close(fd);
Bẫy quan trọng nhất cho lập trình mạng. read() có thể trả về ít hơn số byte bạn xin, dù chưa hết dữ liệu. Trên socket điều này xảy ra thường xuyên. Luôn dùng vòng lặp và luôn dùng giá trị n trả về, không giả định đã đọc đủ.
Bài tập
  1. Viết chương trình sao chép file, dùng open/read/write.
  2. Mở file không tồn tại rồi in errno và strerror(errno).
  3. Viết hàm ssize_t doc_du(int fd, void *buf, size_t n) lặp cho tới khi đọc đủ n byte — đây chính là hàm readn trong UNP.

E6 goto cleanup — cách C thật sự xử lý lỗi 2,5 giờ›

Mục tiêu. Viết được hàm có 5 bước, mỗi bước có thể hỏng, mà không rò rỉ tài nguyên và không lồng if sâu 5 tầng.

Vì sao đơn vị này tồn tại

E5 dạy bạn errno — biết lỗi. Đơn vị này dạy cấu trúc khi có lỗi. Java có try/finally; C không có gì cả. Nếu bạn mở file, cấp phát bộ nhớ, mở socket, rồi bước thứ tư hỏng — phải dọn ba thứ trước, đúng thứ tự ngược. Không có đơn vị này thì code của bạn rò rỉ ở mọi nhánh lỗi.

Cách sai — lồng sâu, lặp lại lệnh dọn
int lam_viec(void)
{
    FILE *f = fopen("a.txt", "r");
    if (f) {
        char *buf = malloc(1024);
        if (buf) {
            int fd = socket(AF_INET, SOCK_STREAM, 0);
            if (fd >= 0) {
                /* việc thật ở đây, thụt lề 4 tầng */
                close(fd); free(buf); fclose(f);
                return 0;
            }
            free(buf); fclose(f); return -1;   // lặp lại
        }
        fclose(f); return -1;                   // lặp lại
    }
    return -1;
}
Cách đúng — một lối ra, dọn theo bậc thang
int lam_viec(void)
{
    FILE *f   = NULL;
    char *buf = NULL;
    int   fd  = -1;
    int   ret = -1;               // mặc định là THẤT BẠI

    f = fopen("a.txt", "r");
    if (!f)   { perror("fopen");  goto xong; }

    buf = malloc(1024);
    if (!buf) { perror("malloc"); goto dong_file; }

    fd = socket(AF_INET, SOCK_STREAM, 0);
    if (fd < 0) { perror("socket"); goto giai_phong; }

    /* việc thật, thụt lề đúng một tầng */
    ret = 0;                      // chỉ đặt 0 khi mọi thứ đã xong

    close(fd);
giai_phong:
    free(buf);
dong_file:
    fclose(f);
xong:
    return ret;
}

Ba luật của khuôn mẫu này:

  1. Khởi tạo mọi tài nguyên về giá trị "chưa có" (NULL, -1) ngay đầu hàm.
  2. Nhãn xếp theo thứ tự ngược với thứ tự cấp phát.
  3. ret mặc định là lỗi, chỉ đặt thành công ở đúng một chỗ.

Đây không phải mẹo lạ — đây là khuôn mẫu chuẩn trong nhân Linux, trong OpenSSL, trong libcurl. Bạn sẽ gặp nó ở mọi mã nguồn C nghiêm túc. Lời khuyên "đừng bao giờ dùng goto" áp dụng cho nhảy lung tung, không áp dụng cho nhảy tiến tới khối dọn dẹp.

assert — bắt lỗi của chính bạn, không phải lỗi của người dùng
#include <assert.h>

void gui(int fd, const char *buf, size_t n)
{
    assert(buf != NULL);      // LỖI LẬP TRÌNH: không được xảy ra
    assert(fd >= 0);
    // còn "mạng đứt" thì KHÔNG dùng assert — đó là chuyện bình thường,
    // phải kiểm bằng if và trả mã lỗi.
}

Ranh giới: assert cho điều không thể sai nếu code đúng; if + errno cho điều có thể sai dù code đúng (file không có, mạng đứt, hết bộ nhớ). Biên dịch với -DNDEBUG thì mọi assert biến mất hoàn toàn — nên không bao giờ đặt lệnh có tác dụng phụ vào trong assert: assert(x = doc()); là lỗi kinh điển.

Bẫy. Nhảy goto qua mặt một khai báo có khởi tạo thì biến đó ở trạng thái chưa xác định khi tới nhãn. Vì thế phải khai báo tất cả tài nguyên ở đầu hàm, trước cái goto đầu tiên.
Bài tập
  1. Viết lại một hàm bất kỳ bạn đã làm ở C2 hoặc E5 theo khuôn mẫu goto cleanup.
  2. Viết int chep_file(const char *nguon, const char *dich): mở hai file, cấp bộ đệm 4096, chép, đóng. Xử lý đủ 4 nhánh lỗi. Thử với file nguồn không tồn tại và với thư mục đích không ghi được, kiểm bằng valgrind rằng cả hai nhánh đều không rò rỉ.
  3. Thêm assert vào hàm danh sách liên kết ở D4. Rồi biên dịch với -DNDEBUG, truyền NULL vào, xem khác nhau thế nào.

F2 Giải mã code socket và viết server đầu tiên 4 giờ›

Mục tiêu. Đọc trôi dòng bind() và viết được một server echo bằng C.

Giải mã dòng kiểm tra
if (bind(sockfd, (struct sockaddr *)&servaddr, sizeof(servaddr)) < 0)
    perror("bind");
  • sockfd — mô tả file, một số nguyên → E5
  • &servaddr — lấy địa chỉ của struct → B1, D2
  • (struct sockaddr *) — ép kiểu con trỏ → B2, D1
  • sizeof(servaddr) — kích thước struct → A2, D1
  • < 0 — quy ước trả lỗi của Unix → E5
  • perror — in errno → E5

Sáu đơn vị bạn đã học hội tụ vào một dòng. Nếu chỗ nào còn mơ hồ, quay lại đúng đơn vị đó.

Khung server echo
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>

#define CONG 5000

int main(void)
{
    int listenfd = socket(AF_INET, SOCK_STREAM, 0);
    if (listenfd < 0) { perror("socket"); return 1; }

    struct sockaddr_in servaddr;
    memset(&servaddr, 0, sizeof(servaddr));      // xóa sạch trước khi điền
    servaddr.sin_family      = AF_INET;
    servaddr.sin_addr.s_addr = htonl(INADDR_ANY);
    servaddr.sin_port        = htons(CONG);      // E2: đổi thứ tự byte

    if (bind(listenfd, (struct sockaddr *)&servaddr, sizeof(servaddr)) < 0) {
        perror("bind"); return 1;
    }
    if (listen(listenfd, 10) < 0) { perror("listen"); return 1; }

    printf("Dang nghe o cong %d...\n", CONG);

    for (;;) {
        struct sockaddr_in cli;
        socklen_t len = sizeof(cli);             // B4: giá trị-kết quả
        int connfd = accept(listenfd, (struct sockaddr *)&cli, &len);
        if (connfd < 0) { perror("accept"); continue; }

        char buf[1024];
        ssize_t n;
        while ((n = read(connfd, buf, sizeof(buf))) > 0)
            write(connfd, buf, n);               // E5: ghi đúng n byte

        close(connfd);
    }
    return 0;
}
Lưu ý. Chương trình này cần Linux — trên WSL2 biên dịch gcc -Wall server.c -o server rồi thử bằng telnet localhost 5000 hoặc nc localhost 5000. Trên Windows thuần thì <arpa/inet.h> không tồn tại.
Bài tập
  1. Biên dịch và chạy server trên, kết nối bằng nc.
  2. Thêm in ra địa chỉ IP client bằng inet_ntoa(cli.sin_addr).
  3. Bỏ htons đi, chạy lại, dùng ss -tlnp xem server thật sự nghe ở cổng nào. Đây là bài học đắt giá nhất của E2.

  • Makefile / CMakeLists.txt — cho biết file nào thật sự được biên dịch, và -D nào đang bật.

Tới đây bạn viết được C nhưng vẫn coi máy tính là hộp đen. Giai đoạn này mở hộp ra: thanh ghi, assembly, khung ngăn xếp, cache, bộ nhớ ảo. Sau G, những câu như "con trỏ treo", "tràn bộ đệm", "cache miss" thôi là ẩn dụ — bạn nhìn thấy chúng. Đây là phần lộ trình cũ thiếu hẳn.

G1 CPU, thanh ghi, và chu kỳ lệnh 3 giờ›

Mục tiêu. Biết một biến C thật sự nằm ở đâu, và vì sao "nằm ở đâu" quyết định tốc độ gấp trăm lần.

Khái niệm

CPU chỉ làm được ba việc, lặp mãi: nạp lệnh từ bộ nhớ → giải mã → thực thi. Nó không hiểu biến, không hiểu hàm, không hiểu kiểu dữ liệu.

Thanh ghi là ô nhớ nằm ngay trong CPU. x86-64 có 16 thanh ghi đa dụng 64 bit: %rax %rbx %rcx %rdx %rsi %rdi %rbp %rsp %r8–%r15. Ngoài ra %rip giữ địa chỉ lệnh kế tiếp, và thanh ghi cờ giữ kết quả so sánh gần nhất.

Con số phải thuộc:

Nơi đọc Thời gian So sánh
Thanh ghi ~0,3 ns 1 nhịp
Cache L1 ~1 ns 4 nhịp
RAM ~80 ns 250 nhịp
SSD ~100 µs 300 000 nhịp
Gói mạng trong nước ~20 ms 60 triệu nhịp

Nhìn dòng cuối: một chuyến đi mạng bằng 60 triệu lệnh CPU. Đó là lý do mọi kỹ thuật tối ưu server đều xoay quanh giảm số lần đi mạng và số lần gọi hệ thống, chứ không phải tối ưu vòng lặp.

Nhìn tận mắt
// t.c
int cong(int a, int b) { return a + b; }
$ gcc -O2 -S t.c -o -    # -S = dừng ở assembly, đừng dịch tiếp

cong:
    leal    (%rdi,%rsi), %eax   # a ở %rdi, b ở %rsi, kết quả vào %eax
    ret

Cả một hàm C = hai lệnh máy. Không có biến a, không có biến b — chúng chỉ là thanh ghi. Quy ước "tham số thứ nhất vào %rdi, thứ hai vào %rsi, giá trị trả về ở %rax" gọi là quy ước gọi hàm, học kỹ ở G3.

Bẫy khi học. Biên dịch -O0 (mặc định) ra assembly dài và ngớ ngẩn vì mọi biến đều đổ ra bộ nhớ. Biên dịch -O2 ra assembly ngắn nhưng đã bị tối ưu tới mức khó lần lại C gốc. Học thì đọc -O0 trước cho dễ hiểu ánh xạ, rồi mới xem -O2 để thấy trình biên dịch giỏi cỡ nào.
Bài tập
  1. Viết hàm 5 dòng bất kỳ, chạy gcc -O0 -S và gcc -O2 -S, đếm số dòng assembly mỗi bên.
  2. Mở godbolt.org, dán code vào, bật màu ánh xạ dòng C ↔ dòng assembly. Dành 30 phút chỉ để nghịch.
  3. Viết hàm có 8 tham số. Xem assembly: tham số thứ 7 và 8 đi đâu? (Gợi ý: hết thanh ghi rồi.)

G2 Đọc assembly x86-64 ở mức đủ dùng 5 giờ›

Mục tiêu. Không phải viết assembly. Chỉ cần đọc được, để khi gdb dừng ở một địa chỉ lạ bạn còn biết chuyện gì đang xảy ra.

Mười lệnh chiếm 90% mã sinh ra
Lệnh Nghĩa Tương đương C

Cách đọc toán hạng

Cú pháp AT&T (mặc định của gcc): nguồn trước, đích sau — ngược với Intel. Hậu tố cho biết kích thước: b=1 byte, w=2, l=4, q=8.

movl  $5, -4(%rbp)      # ghi số 5 (4 byte) vào ô cách %rbp 4 byte về phía dưới
                        # tức: một biến int cục bộ = 5

movq  (%rdi), %rax      # ĐỌC nội dung tại địa chỉ trong %rdi
                        # tức: rax = *rdi   -- đây là giải tham chiếu con trỏ

movq  %rdi, %rax        # chép chính con trỏ, không đọc
                        # tức: rax = rdi

Khác biệt giữa hai dòng cuối chính là khác biệt giữa *p và p — thứ bạn học ở B2, giờ nhìn thấy được.

Vòng lặp trông thế nào
// C:  for (i = 0; i < 10; i++) tong += i;

    movl  $0, %eax          # i = 0
    movl  $0, %edx          # tong = 0
.L2:
    addl  %eax, %edx        # tong += i
    addl  $1, %eax          # i++
    cmpl  $10, %eax         # so i với 10
    jne   .L2               # chưa bằng thì quay lại

Không có for. Chỉ có so sánh và nhảy. Mọi cấu trúc điều khiển ở A5 đều quy về đúng hai thứ này.

Bẫy. lea trông giống mov nhưng không đọc bộ nhớ. Trình biên dịch hay dùng lea để làm phép nhân và cộng cùng lúc (lea (%rdi,%rsi,4), %rax = rdi + rsi*4), nên thấy lea đừng vội tưởng là lấy địa chỉ.
Bài tập
  1. Viết hàm có if/else, dịch -O0 -S, khoanh vùng đâu là nhánh đúng, đâu là nhánh sai, đâu là chỗ hai nhánh gặp lại.
  2. objdump -d a.out | less, tìm hàm main, đọc từ đầu tới lệnh call đầu tiên. Nói được nó gọi hàm gì.
  3. Viết hàm int lay(int *p) { return *p; } và int lay2(int *p) { return p[3]; }. So hai bản assembly, chỉ ra con số 12 nằm ở đâu và vì sao là 12 chứ không phải 3.

G3 Khung ngăn xếp — hàm được gọi thế nào, và tràn bộ đệm thật sự là gì 4 giờ›

Mục tiêu. Vẽ được ngăn xếp tại một thời điểm bất kỳ, và giải thích bằng địa chỉ cụ thể vì sao gets() có thể cho kẻ tấn công chiếm quyền điều khiển.

Đây là chỗ nối B5, C1 và G2

B5 nói "tràn bộ đệm là nguy hiểm". C1 nói "biến cục bộ nằm trên stack". Nhưng chưa đơn vị nào nói cạnh biến cục bộ là cái gì. Câu trả lời — địa chỉ trở về — chính là toàn bộ câu chuyện.

Một khung ngăn xếp
       địa chỉ CAO
   ┌──────────────────────┐
   │  tham số thứ 7, 8... │   (nếu có, hết thanh ghi rồi)
   ├──────────────────────┤
   │  ĐỊA CHỈ TRỞ VỀ      │  <── lệnh call đẩy vào đây
   ├──────────────────────┤
   │  %rbp cũ             │  <── %rbp trỏ vào đây
   ├──────────────────────┤
   │  buf[64]             │
   │  ...                 │   biến cục bộ
   │  int n               │
   └──────────────────────┘  <── %rsp trỏ vào đây
       địa chỉ THẤP

   Ngăn xếp mọc XUỐNG (địa chỉ giảm dần).
   Nhưng ghi vào mảng thì đi LÊN (địa chỉ tăng dần).
   Hai chiều ngược nhau — đó là toàn bộ vấn đề.
Mở đầu và kết thúc hàm
ham:
    pushq  %rbp          # lưu khung của người gọi
    movq   %rsp, %rbp    # khung mới bắt đầu từ đây
    subq   $80, %rsp     # chừa 80 byte cho biến cục bộ
    ...
    leave                # = movq %rbp,%rsp ; popq %rbp
    ret                  # lấy địa chỉ trở về khỏi stack, nhảy tới đó

Chú ý dòng subq $80, %rsp: cấp phát biến cục bộ là một phép trừ. Đó là lý do stack nhanh hơn heap hàng chục lần — malloc phải đi tìm chỗ trống, còn stack chỉ trừ một con số.

Tràn bộ đệm, nhìn từ ngăn xếp
void doc_ten(void)
{
    char buf[8];
    gets(buf);          // gets KHÔNG kiểm độ dài. Đã bị xóa khỏi chuẩn C11.
    printf("%s\n", buf);
}

Gõ 8 ký tự: vừa đủ. Gõ 16 ký tự: 8 byte đầu vào buf, 8 byte sau đè lên %rbp cũ. Gõ 24 ký tự: đè lên địa chỉ trở về. Khi ret chạy, CPU lấy 8 byte đó làm địa chỉ lệnh kế tiếp và nhảy tới. Nếu 8 byte đó do kẻ tấn công chọn, chúng quyết định chương trình chạy tiếp ở đâu.

Đó là lỗ hổng stack smashing — cùng một cơ chế với sâu Morris năm 1988 và hàng nghìn CVE từ đó tới nay. Nó không phải chuyện lý thuyết: nó là lý do strcpy, sprintf, gets bị coi là hàm cấm.

Ba lớp phòng vệ hiện đại (và vì sao vẫn phải cẩn thận)
  • Stack canary — gcc chèn một số ngẫu nhiên ngay trước địa chỉ trở về, kiểm trước khi ret. Bạn thấy nó khi chương trình in *** stack smashing detected ***.
  • NX / DEP — vùng stack bị đánh dấu không thực thi được, nên không nhảy vào mã nạp trên stack. Kẻ tấn công chuyển sang kỹ thuật ROP, ghép các mẩu mã có sẵn.
  • ASLR — địa chỉ nạp ngẫu nhiên mỗi lần chạy, khó đoán chỗ nhảy tới.

Cả ba đều là làm khó, không phải vá. Cách vá duy nhất vẫn là kiểm độ dài trước khi ghi.

Bẫy. Con trỏ trả về từ C1 (trả địa chỉ biến cục bộ) giờ đã rõ: khung ngăn xếp không bị xóa khi hàm kết thúc, chỉ là %rsp dịch lên. Dữ liệu vẫn còn — nên đôi khi code sai vẫn "chạy đúng", cho tới lần gọi hàm sau đè lên. Loại lỗi tệ nhất: lỗi không ổn định.
Bài tập
  1. Viết hàm a() gọi b() gọi c(). Chạy gdb, dừng trong c, gõ bt, rồi info frame. Ghi lại địa chỉ %rbp và %rsp của cả ba khung. Vẽ ra giấy.
  2. Viết chương trình có char buf[8] và strcpy từ argv[1]. Chạy với 5 ký tự, 20 ký tự, 100 ký tự. Ghi lại thông báo lỗi từng lần.
  3. Biên dịch lại bài 2 với -fno-stack-protector -z execstack và chạy setarch -R ./a.out (tắt ASLR). Quan sát hành vi đổi thế nào. Chỉ làm trên máy của bạn, để hiểu — không để tấn công ai.

G4 Phân cấp bộ nhớ và cache — vì sao thứ tự duyệt mảng đổi tốc độ 10 lần 4 giờ›

Mục tiêu. Tự tay đo được hiệu ứng cache, và từ đó biết viết vòng lặp nhanh mà không cần đoán mò.

Khái niệm

RAM chậm gấp ~250 lần thanh ghi (bảng ở G1). CPU giấu độ chậm đó bằng cache — bộ nhớ nhỏ, nhanh, nằm sát lõi. Ba tầng: L1 (~32 KB, 4 nhịp), L2 (~256 KB, 12 nhịp), L3 (~8 MB, 40 nhịp).

Luật quan trọng nhất: cache không nạp từng byte, nó nạp cả một dòng cache 64 byte. Đọc a[0] thì a[1]…a[15] (nếu là int) đã sẵn trong cache, gần như miễn phí.

Từ đó ra hai nguyên tắc:

  • Cục bộ về không gian — dùng dữ liệu nằm gần nhau.
  • Cục bộ về thời gian — dùng lại dữ liệu vừa dùng.
Thí nghiệm bắt buộc phải tự chạy
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define N 4096
static int a[N][N];      // 64 MB — lớn hơn mọi cache

int main(int argc, char **argv)
{
    // PHẢI ghi vào mảng trước. Để mảng static toàn 0 thì gcc biết
    // kết quả chắc chắn là 0 và xóa sạch hai vòng lặp -- bạn đo được
    // 0,005 giây cả hai bản và tưởng cache không quan trọng. Đây là lỗi
    // đo đạc kinh điển: trình biên dịch xóa mất thứ bạn định đo.
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            a[i][j] = i + j;

    clock_t t0 = clock();
    unsigned long long tong = 0;      // long 32 bit sẽ tràn (nhớ A7)

    if (argc > 1 && argv[1][0] == 'c') {
        // duyệt theo CỘT: mỗi bước nhảy 4096*4 = 16 KB
        // -> mỗi lần đọc là một dòng cache mới, dùng 4 byte rồi bỏ
        for (int j = 0; j < N; j++)
            for (int i = 0; i < N; i++)
                tong += a[i][j];
    } else {
        // duyệt theo HÀNG: đi tuần tự trong bộ nhớ
        // -> một dòng cache 64 byte phục vụ 16 lần đọc
        for (int i = 0; i < N; i++)
            for (int j = 0; j < N; j++)
                tong += a[i][j];
    }

    printf("%llu  %.3f giay\n", tong, (double)(clock()-t0)/CLOCKS_PER_SEC);
    return 0;
}
$ gcc -O1 t.c -o t     # -O1 thôi, -O2 gcc sẽ tự hoán vị vòng lặp
$ ./t h                # theo hàng
$ ./t c                # theo cột

Cùng một phép tính, cùng số lệnh, chỉ khác thứ tự duyệt. Chênh lệch thường 10–30 lần. Trên máy dùng để soạn lộ trình này, gcc -O1 đo được 0,009 giây theo hàng và 0,298 giây theo cột — chênh 33 lần. Không có dòng C nào trong chương trình cho thấy điều đó — nó nằm ở phần cứng.

Đo bằng công cụ
$ perf stat -e cache-references,cache-misses,L1-dcache-load-misses ./t c

So tỉ lệ trượt cache giữa hai lần chạy. Đây là lần đầu bạn đo được thứ mà trước giờ chỉ nghe kể.

Áp vào code mạng
  • Mảng struct client clients[1000] duyệt tuần tự nhanh hơn danh sách liên kết (D4) rải rác khắp heap — dù cùng độ phức tạp O(n). Đây là lý do các server hiệu năng cao dùng mảng thay vì danh sách liên kết.
  • Sắp trường hay dùng vào đầu struct, để chúng lọt cùng một dòng cache.
  • False sharing: hai luồng ghi vào hai biến khác nhau nhưng cùng một dòng cache 64 byte → cache line bị giằng qua lại, chậm thảm hại. Sẽ gặp lại ở H4.
Bẫy khi đo. -O2 có thể phát hiện và hoán vị vòng lặp, làm hai bản chạy như nhau và bạn tưởng cache không quan trọng. Dùng -O1, hoặc thêm volatile vào tong (nhớ B7).
Bài tập
  1. Chạy thí nghiệm trên, ghi lại hai con số. Đây là con số của máy bạn, không phải của sách.
  2. Hạ N xuống 64 (mảng 16 KB, lọt L1). Chạy lại. Chênh lệch còn không? Giải thích.
  3. Viết chương trình dò kích thước dòng cache: đọc mảng với bước nhảy 1, 2, 4, 8, 16, 32, 64, 128 byte, đo thời gian mỗi lần. Vẽ biểu đồ — chỗ thời gian ngừng tăng chính là kích thước dòng cache. Kiểm lại bằng getconf LEVEL1_DCACHE_LINESIZE.

G5 Căn chỉnh, đệm, và biểu diễn dữ liệu ở mức bit 3 giờ›

Mục tiêu. Giải thích chính xác vì sao sizeof(struct) lớn hơn tổng các trường, và vì sao điều đó khiến bạn không được gửi thẳng struct qua mạng.

Căn chỉnh

Phần cứng đọc bộ nhớ theo khối. Một int 4 byte nằm ở địa chỉ chia hết cho 4 thì đọc trong một lần; nằm lệch thì phải đọc hai lần rồi ghép. Trên x86 điều này chỉ chậm; trên ARM cũ nó là lỗi phần cứng làm sập chương trình.

Nên trình biên dịch tự chèn byte đệm để mọi trường nằm đúng chỗ.

#include <stdio.h>
#include <stddef.h>

struct xau {
    char  a;      // offset 0
                  // 3 byte đệm
    int   b;      // offset 4  (phải chia hết cho 4)
    char  c;      // offset 8
                  // 7 byte đệm
    double d;     // offset 16 (phải chia hết cho 8)
};                // tổng: 24 byte, dù chỉ 14 byte dữ liệu

struct dep {
    double d;     // offset 0
    int    b;     // offset 8
    char   a;     // offset 12
    char   c;     // offset 13
};                // tổng: 16 byte — chỉ đổi thứ tự khai báo

int main(void)
{
    printf("xau = %zu, dep = %zu\n", sizeof(struct xau), sizeof(struct dep));
    printf("b o offset %zu\n", offsetof(struct xau, b));
    return 0;
}

Luật: sắp trường từ lớn tới nhỏ thì đệm ít nhất. Với một server giữ 100 000 struct client, 8 byte thừa mỗi cái là 800 KB — đủ để đẩy dữ liệu ra khỏi cache L3 (nhớ G4).

Vì sao không gửi thẳng struct qua mạng

Ba lý do, mỗi lý do đủ để hỏng:

  1. Đệm khác nhau giữa hai máy / hai trình biên dịch → lệch trường.
  2. Thứ tự byte khác nhau (E2) → số bị đảo.
  3. Con trỏ trong struct → địa chỉ vô nghĩa ở máy khác.

Đây là cầu nối trực tiếp tới I1, nơi bạn học cách đóng gói thủ công.

Ép bỏ đệm — và cái giá
struct __attribute__((packed)) goi_tin {
    uint8_t  loai;
    uint32_t do_dai;     // giờ nằm ở offset 1, KHÔNG căn chỉnh
};

Được cái gọn đúng 5 byte, mất cái mọi lần truy cập do_dai đều lệch — chậm trên x86, sập trên ARM. Và lấy địa chỉ trường trong struct packed (&g.do_dai) là hành vi không xác định. Dùng khi đọc định dạng file/giao thức có sẵn, đừng dùng làm mặc định.

Bẫy. sizeof(struct) còn được làm tròn lên bội số của trường lớn nhất, để mảng struct vẫn căn chỉnh. Vì thế struct { double d; char c; } là 16 byte chứ không phải 9.
Bài tập
  1. Chạy ví dụ. Rồi tự tính bằng tay sizeof của struct { char a; short b; char c; long d; } trước khi chạy để kiểm.
  2. Dùng offsetof in vị trí từng trường của struct sockaddr_in. Đối chiếu với định nghĩa trong /usr/include/netinet/in.h.
  3. Khai báo struct 5 trường theo thứ tự xấu nhất rồi tốt nhất. In hai sizeof. Tính xem với 1 triệu bản ghi thì tiết kiệm bao nhiêu MB.

G6 Bộ nhớ ảo — chuyện gì thật sự xảy ra khi bạn gọi malloc 4 giờ›

Mục tiêu. Hiểu segfault là một ngoại lệ phần cứng, và hiểu vì sao hai chương trình cùng in ra địa chỉ 0x7fff... mà không đè lên nhau.

Khái niệm

Địa chỉ trong chương trình C của bạn không phải địa chỉ RAM thật. Nó là địa chỉ ảo. Giữa hai thứ có phần cứng MMU và một bảng tra do nhân hệ điều hành dựng.

Bộ nhớ chia thành trang 4096 byte. Mỗi tiến trình có bảng trang riêng ánh xạ trang ảo → khung vật lý. Vì bảng riêng nên:

  • Hai tiến trình dùng cùng địa chỉ ảo mà trỏ vào hai chỗ RAM khác nhau — cách ly.
  • Một trang có thể nằm trên đĩa thay vì RAM — tráo trang.
  • Nhiều tiến trình dùng chung một khung vật lý cho cùng thư viện — chia sẻ.
  • Trang có cờ đọc/ghi/thực thi — nền tảng của NX ở G3.
Segfault, giải thích đầy đủ

Bạn giải tham chiếu con trỏ NULL. MMU tra bảng trang cho địa chỉ 0, thấy không có ánh xạ. Phần cứng phát sinh lỗi trang — một ngoại lệ, CPU nhảy vào nhân. Nhân xem: đây có phải trang hợp lệ đang nằm trên đĩa không? Không. Vậy tiến trình truy cập bậy → nhân gửi tín hiệu SIGSEGV → tiến trình chết.

Nên "segmentation fault" không phải lỗi do C, cũng không do gcc. Nó là CPU và nhân bắt quả tang chương trình bạn. Và cũng vì thế: nếu con trỏ hỏng lại trỏ vào một trang đang hợp lệ (ví dụ con trỏ treo trỏ vào vùng heap vẫn còn ánh xạ), thì không có segfault — chương trình chạy tiếp với dữ liệu rác. Đó là lý do lỗi bộ nhớ ở C2 khó tìm hơn nhiều so với sập ngay.

malloc thật sự làm gì
$ strace -e trace=brk,mmap ./a.out

malloc không phải lời gọi hệ thống. Nó là hàm thư viện, quản lý một vùng nhớ đã xin sẵn. Chỉ khi hết mới xin thêm từ nhân qua brk() (nới đỉnh heap) hoặc mmap() (xin vùng mới, dùng cho khối lớn, thường > 128 KB).

Chạy strace trên chương trình gọi malloc(10) một triệu lần — bạn sẽ thấy rất ít lời gọi hệ thống. Đó là lý do malloc nhanh hơn bạn tưởng, nhưng vẫn chậm hơn stack hàng chục lần (G3).

// Cấp phát lười: xin 1 GB thành công ngay, dù máy có 8 GB
// vì nhân chỉ ghi vào bảng trang, chưa cấp RAM thật.
// RAM chỉ được cấp khi bạn CHẠM vào từng trang.
char *p = malloc(1024L*1024*1024);
printf("xin xong\n");           // in ra ngay

for (long i = 0; i < 1024L*1024*1024; i += 4096)
    p[i] = 1;                   // giờ mới thật sự tốn RAM,
                                   // mỗi dòng này là một lỗi trang

Bẫy. Vì cấp phát lười, malloc trả về khác NULL không bảo đảm bạn có RAM. Chương trình có thể bị OOM killer giết sau đó, ở giữa vòng lặp, không có mã lỗi nào. Trên Linux đây là hành vi mặc định (vm.overcommit_memory).

H1 Lời gọi hệ thống — biên giới giữa code bạn và nhân 3 giờ›

H2 Tiến trình: fork, exec, wait và bảng mô tả tệp 4 giờ›

Mục tiêu. Viết được server TCP kiểu fork — kiến trúc server đầu tiên trong lịch sử, và vẫn là kiến trúc dễ hiểu nhất.

fork — một lời gọi, hai lần trả về
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>

int main(void)
{
    pid_t pid = fork();

    if (pid < 0)  { perror("fork"); return 1; }

    if (pid == 0) {
        // TIẾN TRÌNH CON: fork trả về 0
        printf("con,  pid=%d, cha=%d\n", getpid(), getppid());
        _exit(0);            // _exit chứ không exit — không xả đệm của cha
    }

    // TIẾN TRÌNH CHA: fork trả về pid của con
    printf("cha,  pid=%d, con=%d\n", getpid(), pid);

    int trang_thai;
    waitpid(pid, &trang_thai, 0);       // không wait -> con thành xác sống
    if (WIFEXITED(trang_thai))
        printf("con thoat voi ma %d\n", WEXITSTATUS(trang_thai));
    return 0;
}

Sau fork, con là bản sao gần như hoàn toàn của cha: cùng mã lệnh, cùng biến, cùng file đang mở. Khác ở: pid, giá trị trả về của fork, và bộ đếm thời gian.

Bản sao đó không thật sự chép bộ nhớ. Nhân đánh dấu mọi trang là chỉ đọc và dùng chung; khi một bên ghi mới chép trang đó ra. Gọi là sao chép khi ghi — và bạn hiểu được nó chỉ vì đã học bảng trang ở G6.

Bảng mô tả tệp — nền tảng của mọi thứ trong Unix

Mỗi tiến trình có một mảng. Chỉ số của mảng là fd. Ô 0 là stdin, 1 stdout, 2 stderr, các ô sau do open, socket, accept cấp. Nhân luôn cấp số nhỏ nhất còn trống — tính chất này làm nên dup2 và toàn bộ cơ chế chuyển hướng của shell.

Sau fork, con thừa hưởng cả bảng. Cả cha và con cùng trỏ vào một mô tả file trong nhân — dùng chung cả vị trí đọc ghi. Đây là điểm mấu chốt của server fork: con nhận được socket của client mà không cần truyền gì cả.

Server TCP kiểu fork
while (1) {
    int fd_client = accept(fd_nghe, NULL, NULL);
    if (fd_client < 0) { if (errno == EINTR) continue; perror("accept"); break; }

    pid_t pid = fork();
    if (pid == 0) {
        close(fd_nghe);          // con KHÔNG cần socket nghe
        phuc_vu(fd_client);
        close(fd_client);
        _exit(0);
    }
    close(fd_client);            // cha KHÔNG cần socket client
}

Hai dòng close là chỗ 90% người mới viết sai. Nếu cha quên close(fd_client): bảng fd của cha đầy dần, sau vài nghìn client là accept trả EMFILE. Nếu con quên close(fd_nghe): cha không thể tắt cổng vì vẫn còn tham chiếu.

So với code Java của bạn: new Thread(() -> phucVu(socket)).start() làm cùng một việc, nhưng bằng luồng chứ không bằng tiến trình. Khác biệt về giá: fork tốn ~1 ms và một bảng trang; tạo luồng tốn ~30 µs và dùng chung bộ nhớ. Đó là lý do H4 tồn tại.

exec — thay ruột, giữ vỏ

execve không tạo tiến trình mới. Nó vứt bỏ toàn bộ ảnh bộ nhớ hiện tại và nạp chương trình khác vào cùng pid. Bảng fd vẫn giữ nguyên (trừ fd có cờ close-on-exec). Cặp fork+exec chính là cách shell chạy mọi lệnh.

Bẫy: tiến trình xác sống. Con thoát mà cha không wait thì mục ghi vẫn nằm trong bảng tiến trình mãi mãi (ps hiện <defunct>). Server fork chạy lâu sẽ đầy bảng. Cách sửa: bắt SIGCHLD rồi waitpid(-1, NULL, WNOHANG) trong vòng lặp — cần H3.

  2. Viết chương trình tự cài lại chính nó: fork, con execlp("ls", "ls", "-l", NULL), cha wait rồi in mã thoát.

H3 Tín hiệu — vì sao server chết khi client ngắt kết nối 3 giờ›

Mục tiêu. Xử lý được SIGPIPE, SIGCHLD, SIGINT — ba tín hiệu mà mọi server đều gặp trong ngày đầu tiên chạy thật.

Khái niệm

Tín hiệu là ngắt mềm: nhân dừng luồng thực thi bình thường, chạy hàm xử lý của bạn, rồi quay lại chỗ cũ. Nó bất đồng bộ — có thể xảy ra giữa hai lệnh máy bất kỳ, kể cả giữa hai nửa của một phép gán 64 bit.

SIGPIPE ghi vào socket phía kia đã đóng giết tiến trình

SIGPIPE — lỗi làm sập server nhiều nhất

Client tắt cửa sổ. Server vẫn đang write(). Nhân gửi SIGPIPE, mặc định là giết chết server — cả server, không chỉ một kết nối. Một client bực mình có thể tắt cả dịch vụ.

signal(SIGPIPE, SIG_IGN);       // làm ngay dòng đầu của main
// Bỏ qua rồi thì write() trả về -1 với errno == EPIPE.
// Giờ bạn xử lý được bằng if, đúng như E5 đã dạy.

Java giấu chuyện này: bạn chỉ thấy IOException: Broken pipe. C bắt bạn tự xử lý — và nhờ đó bạn hiểu cái ngoại lệ kia thật ra là gì.

Hàm xử lý tín hiệu chỉ được làm rất ít việc
#include <signal.h>

static volatile sig_atomic_t phai_dung = 0;   // nhớ B7

static void xu_ly(int sig) { phai_dung = 1; } // CHỈ đặt cờ, không hơn

int main(void)
{
    struct sigaction sa;
    sa.sa_handler = xu_ly;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;        // tự chạy lại lời gọi bị ngắt
    sigaction(SIGINT,  &sa, NULL);   // dùng sigaction, ĐỪNG dùng signal
    sigaction(SIGTERM, &sa, NULL);

    while (!phai_dung) {
        /* vòng lặp phục vụ */
    }
    printf("dang tat dep...\n");     // đóng socket, ghi log, xả đệm
    return 0;
}

Vì sao chỉ đặt cờ? Vì hàm xử lý có thể chen vào giữa lúc chương trình chính đang ở trong malloc. Gọi malloc hoặc printf trong đó có thể làm hỏng cấu trúc nội bộ của thư viện. Danh sách hàm được phép nằm ở man 7 signal-safety — rất ngắn, write có, printf không.

volatile là bắt buộc (B7): không có nó, gcc -O2 giữ phai_dung trong thanh ghi và vòng lặp không bao giờ dừng.

EINTR — lời gọi bị ngắt giữa chừng

Tín hiệu tới khi đang accept() hoặc read() thì lời gọi trả về -1 với errno == EINTR. Đây không phải lỗi thật, chỉ là bị ngắt. Mọi code mạng nghiêm túc đều có:

while ((n = read(fd, buf, sizeof buf)) < 0 && errno == EINTR)
    ;       // bị ngắt thì thử lại
if (n < 0) { perror("read"); }
Bẫy. Tín hiệu không xếp hàng. Mười con thoát cùng lúc có thể chỉ sinh một SIGCHLD. Vì thế hàm xử lý SIGCHLD phải lặp while (waitpid(-1, NULL, WNOHANG) > 0); chứ không gọi một lần.
Bài tập
  1. Viết server đơn giản, kết nối bằng nc, rồi Ctrl-C phía client trong lúc server đang gửi. Server chết. Thêm signal(SIGPIPE, SIG_IGN), làm lại, in errno.
  2. Cài bộ xử lý SIGINT như trên. Kiểm rằng Ctrl-C in "dang tat dep" chứ không chết ngay. Rồi bỏ volatile, dịch -O2, thử lại.
  3. Thêm bộ xử lý SIGCHLD vào server fork ở H2, dùng vòng waitpid(..., WNOHANG). Kết nối rồi ngắt 20 client, kiểm bằng ps rằng không còn xác sống.

H4 Luồng, mutex, và tranh chấp dữ liệu 4 giờ›

Mục tiêu. Tự tay tạo ra một lỗi tranh chấp, nhìn thấy nó, rồi sửa. Đọc lý thuyết về race condition không đủ — phải thấy con số sai.

Luồng khác tiến trình chỗ nào

Tiến trình (H2) có bảng trang riêng → cách ly. Luồng dùng chung mọi thứ: heap, biến toàn cục, bảng fd. Chỉ riêng ngăn xếp là mỗi luồng một cái.

Dùng chung là ưu điểm (truyền dữ liệu không tốn gì) và cũng là toàn bộ vấn đề (ai cũng ghi được vào mọi chỗ).

Tranh chấp — chạy thử để thấy
#include <pthread.h>
#include <stdio.h>

#define N_LUONG 4
#define N_LAP   1000000

long dem = 0;                    // dùng chung, không khóa

void *chay(void *arg)
{
    for (int i = 0; i < N_LAP; i++)
        dem++;                   // KHÔNG nguyên tử
    return NULL;
}

int main(void)
{
    pthread_t t[N_LUONG];
    for (int i = 0; i < N_LUONG; i++)
        pthread_create(&t[i], NULL, chay, NULL);
    for (int i = 0; i < N_LUONG; i++)
        pthread_join(t[i], NULL);

    printf("mong doi %d, thuc te %ld\n", N_LUONG * N_LAP, dem);
    return 0;
}
$ gcc -O2 t.c -o t -lpthread     # nhớ -lpthread
$ ./t
mong doi 4000000, thuc te 1372845     # mỗi lần chạy một số khác

Vì sao mất? Nhờ G2 bạn biết dem++ không phải một lệnh:

movq  dem(%rip), %rax    # 1. đọc
addq  $1, %rax           # 2. cộng
movq  %rax, dem(%rip)    # 3. ghi

Hai luồng đọc cùng giá trị 100, cùng cộng thành 101, cùng ghi 101. Hai lần tăng chỉ ra một. Nhân có thể chuyển luồng ở giữa ba lệnh đó.

Sửa — mutex
pthread_mutex_t khoa = PTHREAD_MUTEX_INITIALIZER;

void *chay(void *arg)
{
    for (int i = 0; i < N_LAP; i++) {
        pthread_mutex_lock(&khoa);
        dem++;                          // vùng tới hạn
        pthread_mutex_unlock(&khoa);
    }
    return NULL;
}

Giờ kết quả luôn đúng — nhưng chậm hơn bản một luồng. Bốn luồng giành nhau một khóa thì phần lớn thời gian là chờ và chuyển ngữ cảnh. Bài học: thêm luồng không đồng nghĩa với nhanh hơn.

Ba công cụ đồng bộ, ba việc khác nhau
  • Mutex — mỗi lần một luồng vào vùng tới hạn.
  • Biến điều kiện — chờ tới khi một điều kiện thành đúng, không quay vòng đốt CPU. Đây là thứ dựng nên hàng đợi công việc trong thread pool (J5).
  • Atomic (<stdatomic.h>) — phép tăng/so-sánh-và-đổi không cần khóa, nhanh hơn nhiều cho biến đơn lẻ.
Công cụ phát hiện
$ gcc -fsanitize=thread -g t.c -o t -lpthread
$ ./t

ThreadSanitizer tìm được cả những tranh chấp chưa hề gây lỗi trong lần chạy đó — thứ mà kiểm thử bằng tay không bao giờ tìm ra.

Bẫy. volatile không sửa được tranh chấp. Nó chỉ cấm trình biên dịch giữ biến trong thanh ghi; nó không làm dem++ thành nguyên tử, và không ngăn CPU sắp xếp lại lệnh. Nhầm lẫn này rất phổ biến. Cần nguyên tử thì dùng mutex hoặc atomic.
Bài tập
  1. Chạy bản không khóa 10 lần, ghi lại 10 con số khác nhau. Đây là bằng chứng bạn cần để không bao giờ quên bài này.
  2. Đo thời gian ba bản: một luồng, bốn luồng có mutex, bốn luồng dùng atomic_long. Xếp hạng và giải thích.
  3. Cho mỗi luồng một biến đếm riêng trong mảng long dem[4], cuối cùng mới cộng lại. Đo — vẫn chậm bất ngờ. Đó là false sharing ở G4: bốn biến nằm cùng một dòng cache 64 byte. Sửa bằng cách giãn ra 64 byte mỗi phần tử, đo lại.

H5 Lập lịch, chuyển ngữ cảnh, và "chặn" thật sự nghĩa là gì 2,5 giờ›

Mục tiêu. Hiểu vì sao 10 000 luồng thì sập mà 10 000 kết nối thì không — câu hỏi dẫn thẳng tới J4.

Chuyển ngữ cảnh tốn gì

Nhân đổi từ luồng A sang luồng B phải: lưu 16 thanh ghi của A, nạp của B, đổi con trỏ ngăn xếp, nếu khác tiến trình thì đổi cả bảng trang và xả TLB. Phần cứng tốn ~1–3 µs, nhưng cái đắt hơn là cache nguội: dữ liệu của B không còn trong L1/L2 (G4), nên vài nghìn lệnh đầu tiên của B chạy chậm.

Con số để nhớ: chuyển ngữ cảnh ≈ 3–10 µs tính cả hiệu ứng cache. So với lời gọi hệ thống ~1 µs (H1) và phép cộng ~0,3 ns (G1).

"Chặn" nghĩa là nhường CPU

Khi bạn gọi read() trên socket chưa có dữ liệu, luồng không hề "chờ". Nhân chuyển nó sang trạng thái ngủ, gỡ khỏi hàng đợi chạy, và cho luồng khác dùng CPU. Khi gói tin tới, card mạng phát ngắt, nhân đánh thức luồng.

Nên một luồng bị chặn không tốn CPU. Nó tốn:

  • Bộ nhớ — mỗi luồng một ngăn xếp, mặc định Linux là 8 MB không gian ảo (thật thì chỉ dùng vài KB, nhờ cấp phát lười ở G6).
  • Chi phí lập lịch — bộ lập lịch phải duyệt danh sách luồng.

Đó là câu trả lời cho bài toán C10K: 10 000 luồng = 80 GB không gian ảo và một bộ lập lịch quá tải. 10 000 kết nối trong một luồng dùng epoll = một mảng fd. Cùng số client, khác kiến trúc hai bậc độ lớn.

Đồng thời khác song song
  • Đồng thời — nhiều việc đang dở cùng lúc. Cần đúng 1 lõi.
  • Song song — nhiều việc đang chạy cùng lúc. Cần nhiều lõi.

Server mạng hầu như luôn là bài toán đồng thời, không phải song song: phần lớn thời gian là chờ mạng chứ không phải tính toán. Đó là lý do Node.js một luồng vẫn phục vụ được nhiều client, và vì sao thêm lõi không giúp gì cho server chủ yếu chờ I/O.

Quan sát

Bẫy khi đo. Thấy CPU 5% mà server vẫn chậm thì đừng tối ưu thuật toán — nút thắt nằm ở I/O hoặc ở khóa (H4). Đo trước, sửa sau. Đây là sai lầm phổ biến nhất khi tối ưu.

Byte trên dây

5 đơn vị · ~1,5 tuần

Giai đoạn này trả lời câu hỏi mà lộ trình cũ bỏ trống hoàn toàn: dữ liệu trong bộ nhớ biến thành byte trên cáp mạng bằng cách nào, và giao thức thật sự là cái gì ở mức từng bit. Học xong I bạn đọc được RFC và bắt gói bằng Wireshark mà hiểu.

I1 Từ struct trong bộ nhớ tới byte trên dây 3 giờ›

Mục tiêu. Viết cặp hàm đóng gói / mở gói thủ công, và hiểu vì sao mọi thư viện tuần tự hóa đều tồn tại.

Đây là chỗ ba đơn vị gặp nhau

D1 dạy struct. E2 dạy endianness. G5 dạy đệm. Ghép lại: không được write(fd, &s, sizeof s). Ba lý do đã nêu ở G5, giờ ta sửa.

Đóng gói thủ công
#include <stdint.h>
#include <string.h>
#include <arpa/inet.h>

struct ban_tin {
    uint8_t  loai;
    uint16_t ma;
    uint32_t thoi_gian;
    char     ten[32];
};

// Trên dây, định dạng CỐ ĐỊNH 39 byte, big-endian:
//   [0]     loai       1 byte
//   [1..2]  ma         2 byte
//   [3..6]  thoi_gian  4 byte
//   [7..38] ten       32 byte
// Không có đệm. Không phụ thuộc trình biên dịch. Đây là ĐẶC TẢ giao thức.

#define KICH_THUOC_DAY 39

size_t dong_goi(const struct ban_tin *m, uint8_t *ra)
{
    size_t i = 0;

    ra[i++] = m->loai;

    uint16_t ma = htons(m->ma);
    memcpy(ra + i, &ma, 2);  i += 2;

    uint32_t tg = htonl(m->thoi_gian);
    memcpy(ra + i, &tg, 4);  i += 4;

    memcpy(ra + i, m->ten, 32);  i += 32;

    return i;               // 39
}

int mo_goi(const uint8_t *vao, size_t n, struct ban_tin *m)
{
    if (n < KICH_THUOC_DAY) return -1;   // LUÔN kiểm độ dài trước

    size_t i = 0;
    m->loai = vao[i++];

    uint16_t ma;  memcpy(&ma, vao + i, 2);  i += 2;
    m->ma = ntohs(ma);

    uint32_t tg;  memcpy(&tg, vao + i, 4);  i += 4;
    m->thoi_gian = ntohl(tg);

    memcpy(m->ten, vao + i, 32);
    m->ten[31] = '\0';                   // ép kết thúc, đừng tin dữ liệu vào
    return 0;
}

Vì sao memcpy chứ không ép kiểu con trỏ? Vì *(uint32_t *)(vao + 3) đọc 4 byte ở địa chỉ lẻ 3 — truy cập lệch (G5), sập trên ARM và là hành vi không xác định theo chuẩn. memcpy luôn an toàn, và trình biên dịch tối ưu nó về đúng một lệnh mov khi được phép.

Ba luật viết đặc tả giao thức
  1. Nói rõ từng byte: vị trí, kích thước, thứ tự byte, ý nghĩa.
  2. Chuỗi thì hoặc độ dài cố định, hoặc có tiền tố độ dài. Đừng dựa vào ký tự \0 từ phía bên kia.
  3. Chừa trường phiên bản ở byte đầu. Không có nó thì không nâng cấp được giao thức mà không làm hỏng client cũ.
Bẫy bảo mật. mo_goi nhận dữ liệu từ Internet — tức từ kẻ có thể cố tình gửi bậy. Không kiểm n trước là tràn bộ đệm đọc (G3). Quy tắc: mọi byte từ mạng là thù địch cho tới khi được kiểm.
Bài tập
  1. Cài đủ hai hàm. Đóng gói rồi mở gói lại, so từng trường. In 39 byte dưới dạng hex và tự đọc bằng mắt.
  2. In sizeof(struct ban_tin). Nó khác 39 — giải thích khoản chênh bằng kiến thức G5.
  3. Cố tình gọi mo_goi(buf, 10, &m). Kiểm rằng nó trả −1 chứ không đọc bậy. Rồi bỏ dòng kiểm độ dài, chạy với -fsanitize=address, đọc báo cáo.

I2 Đóng khung thông điệp — TCP là dòng byte, không phải gói tin 4 giờ›

Mục tiêu. Hiểu và sửa được lỗi mà mọi người viết mạng lần đầu đều mắc. Nếu chỉ học một đơn vị trong giai đoạn I, học đơn vị này.

Lỗi

Client gọi write() ba lần: "XIN", "CHAO", "BAN". Server gọi read() ba lần và tưởng sẽ nhận đúng ba mẩu đó. Sai. Server có thể nhận:

  • "XINCHAOBAN" trong một lần read — TCP gộp lại (thuật toán Nagle)
  • "XIN", "CH", "AOBAN" — chia theo MTU đường truyền
  • "XI", "N", "CHAOB", "AN" — bất kỳ cách chia nào

TCP bảo đảm đúng thứ tự và không mất byte. Nó không bảo đảm ranh giới thông điệp. Ranh giới đó do bạn dựng ở tầng ứng dụng.

UDP thì ngược lại: giữ nguyên ranh giới gói, nhưng có thể mất, có thể đảo thứ tự, có thể tới hai lần. Không có lựa chọn nào cho không.

Cách 1 — tiền tố độ dài
// Trên dây: [4 byte độ dài big-endian][nội dung]

int gui_ban_tin(int fd, const void *data, uint32_t n)
{
    uint32_t do_dai = htonl(n);
    if (ghi_du(fd, &do_dai, 4) < 0) return -1;
    if (ghi_du(fd, data, n)    < 0) return -1;
    return 0;
}

ssize_t nhan_ban_tin(int fd, void *ra, uint32_t toi_da)
{
    uint32_t do_dai;
    if (doc_du(fd, &do_dai, 4) <= 0) return -1;
    do_dai = ntohl(do_dai);

    // BẮT BUỘC: kẻ tấn công gửi do_dai = 4 tỉ để ép bạn malloc 4 GB
    if (do_dai > toi_da) return -1;

    if (doc_du(fd, ra, do_dai) <= 0) return -1;
    return do_dai;
}

doc_du và ghi_du chính là hàm bạn viết ở bài tập E5 — lặp cho tới khi đủ n byte, vì một lần read có thể trả về ít hơn bạn xin. Giờ bạn thấy vì sao bài tập đó quan trọng.

Cách 2 — ký tự phân cách

Dùng \n hoặc \r\n làm dấu hết thông điệp. Đây là cách của HTTP, SMTP, IRC, Redis. Ưu điểm: đọc được bằng mắt, gỡ lỗi bằng telnet được. Nhược: phải quét từng byte tìm dấu phân cách, và phải xử lý trường hợp dữ liệu chứa chính ký tự đó (thoát ký tự, hoặc chuyển sang tiền tố độ dài cho phần thân — đúng như HTTP làm với Content-Length).

Đây là sơ đồ chuẩn của RFC — mỗi hàng 32 bit. Học cách đọc sơ đồ này là đọc được mọi RFC.

  • IHL — độ dài header tính theo đơn vị 4 byte. Giá trị 5 nghĩa là 20 byte. Lớn hơn 5 tức có tùy chọn.
  • Total Length — 16 bit → gói IP tối đa 65 535 byte.
  • TTL — mỗi router giảm 1; về 0 thì vứt gói. Đây là cơ chế traceroute khai thác.
  • Protocol — 6 = TCP, 17 = UDP, 1 = ICMP.
Header TCP — 20 byte, phần quan trọng
  • Cổng nguồn, cổng đích — mỗi cái 16 bit. Bốn số (IP nguồn, cổng nguồn, IP đích, cổng đích) xác định duy nhất một kết nối. Đây là lý do một server nghe một cổng phục vụ được nhiều client.
  • Số thứ tự, số xác nhận — 32 bit mỗi cái. Nền tảng của bảo đảm thứ tự và truyền lại.
  • Cờ: SYN ACK FIN RST PSH URG. Bắt tay ba bước là SYN → SYN+ACK → ACK. Đóng bốn bước là FIN → ACK → FIN → ACK.
  • Cửa sổ — 16 bit, người nhận báo còn chỗ chứa bao nhiêu. Đây là điều khiển luồng, khác với điều khiển tắc nghẽn (do bên gửi tự suy ra từ mất gói).

Header UDP thì chỉ 8 byte: cổng nguồn, cổng đích, độ dài, checksum. Hết. Toàn bộ khác biệt giữa hai giao thức nằm ở 12 byte đó.

I5 Checksum, CRC, và giới hạn thật của bảo đảm TCP 2,5 giờ›

Mục tiêu. Cài được internet checksum, và biết vì sao "TCP bảo đảm dữ liệu đúng" là câu nói không hoàn toàn chính xác.

Internet checksum — 16 bit, bù một
#include <stdint.h>
#include <stddef.h>

uint16_t checksum(const void *du_lieu, size_t n)
{
    const uint16_t *p = du_lieu;
    uint32_t tong = 0;

    while (n > 1) { tong += *p++; n -= 2; }
    if (n)        tong += *(const uint8_t *)p;   // byte lẻ cuối

    // gấp phần tràn (bù một): cộng 16 bit cao vào 16 bit thấp
    while (tong >> 16)
        tong = (tong & 0xFFFF) + (tong >> 16);

    return (uint16_t)~tong;      // đảo bit
}

Bên nhận tính lại checksum trên toàn bộ dữ liệu kể cả trường checksum; nếu kết quả là 0 thì coi như đúng. Mẹo hay của thiết kế này: bên nhận không cần biết trường checksum nằm ở đâu.

Nó yếu tới mức nào

Checksum 16 bit chỉ có 65 536 giá trị. Xác suất một lỗi ngẫu nhiên lọt qua là khoảng 1/65 536. Nghe nhỏ, nhưng với đường truyền 1 Gbit/s liên tục thì vài giờ một lần có gói hỏng lọt qua.

Tệ hơn: phép cộng có tính giao hoán, nên hai byte đổi chỗ cho nhau không đổi checksum — loại lỗi này hoàn toàn vô hình.

CRC32 mạnh hơn nhiều

CRC là phép chia đa thức trên trường nhị phân, phát hiện được mọi lỗi cụm dưới 32 bit và mọi lỗi 1–3 bit. Đó là lý do Ethernet dùng CRC32 ở tầng khung, còn checksum 16 bit chỉ là lớp bảo vệ thứ hai ở tầng IP/TCP.

Điều thật sự phải nhớ

TCP bảo đảm: không mất byte, đúng thứ tự, không lặp. Nó không bảo đảm:

  • Dữ liệu không hỏng — checksum 16 bit là yếu, và có nghiên cứu đo được tỉ lệ lọt lỗi thật trên Internet.
  • Bên kia đã xử lý dữ liệu — write() trả về thành công chỉ nghĩa là byte đã vào đệm gửi của nhân. Ứng dụng bên kia có thể sập ngay sau đó.
  • Dữ liệu không bị hỏng ở nơi khác — bit lật trong RAM router, lỗi ổ cứng, lỗi phần mềm. Checksum chỉ bảo vệ đoạn dây.

Hệ quả thực tế: dữ liệu quan trọng thì tầng ứng dụng phải tự kiểm (SHA-256 cho file tải về), và giao dịch quan trọng thì phải có xác nhận ở tầng ứng dụng, không dựa vào ACK của TCP.

Bẫy trong giáo trình. Nhiều tài liệu tiếng Việt viết "TCP bảo đảm dữ liệu chính xác tuyệt đối". Không đúng — nó bảo đảm ở mức xác suất, và mức đó thấp hơn nhiều người tưởng. Đây là chỗ đáng ghi chú khi ôn thi.
Bài tập
  1. Cài checksum(). Tính cho một mảng bất kỳ, lật một bit, tính lại — xác nhận kết quả đổi.
  2. Tìm hai byte trong mảng và đổi chỗ chúng. Tính lại checksum. Nó không đổi. Bạn vừa tự chứng minh điểm yếu của thuật toán này.
  3. Cài CRC32 bằng bảng tra 256 phần tử. Lặp lại bài 2 — CRC32 phát hiện được. So sánh thời gian chạy hai thuật toán trên 100 MB dữ liệu.

J1 Đệm — vì sao đọc từng byte chậm gấp trăm lần 3 giờ›

Mục tiêu. Đo được chi phí của một lời gọi hệ thống, và từ đó tự quyết được kích thước bộ đệm thay vì chép số 1024 từ sách.

Thí nghiệm
#include <unistd.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

int main(int argc, char **argv)
{
    int co = atoi(argv[1]);              // kích thước bộ đệm
    char *buf = malloc(co);

    int fd = open("dulieu.bin", O_RDONLY);
    clock_t t0 = clock();

    long tong = 0, lan = 0;
    ssize_t n;
    while ((n = read(fd, buf, co)) > 0) { tong += n; lan++; }

    printf("co=%-6d  %ld byte, %ld lan read, %.3f giay\n",
           co, tong, lan, (double)(clock()-t0)/CLOCKS_PER_SEC);
    close(fd); free(buf);
    return 0;
}

Kết quả điển hình: bộ đệm 1 byte mất vài chục giây, bộ đệm 4096 mất vài chục mili giây. Chênh khoảng 1000 lần cho cùng một khối lượng dữ liệu.

Lý do đã học ở H1: mỗi read() là một lần vượt biên vào nhân, tốn ~1 µs bất kể đọc 1 byte hay 4096 byte. Chi phí cố định, nên chia cho càng nhiều byte càng rẻ.

Vì sao 4096 chứ không phải 64

Đường cong phẳng ra ở khoảng 4–64 KB. Không phải ngẫu nhiên:

  • 4096 = một trang bộ nhớ (G6)
  • 4096 = một khối hệ thống tệp trên hầu hết máy
  • Lớn hơn 64 KB thì bộ đệm không lọt cache L2 (G4) và lợi ích mất dần

Kiểm bằng stat -f . xem cột Block size. Và BUFSIZ trong <stdio.h> chính là con số libc chọn sẵn.

Ba tầng đệm chồng nhau
  1. Đệm của thư viện — FILE * của stdio, nằm trong tiến trình bạn. Xả bằng fflush.
  2. Đệm của nhân — page cache cho file, socket buffer cho mạng. Xả bằng fsync (file) — với socket thì không xả được, nhân tự quyết.
  3. Đệm của thiết bị — bộ nhớ đệm trên ổ cứng, hàng đợi trên card mạng.

Ba tầng này giải thích tại sao write() trả về thành công mà dữ liệu vẫn có thể mất khi mất điện — mới qua tầng 2. Và giải thích luôn điểm ở I5: write() thành công không có nghĩa bên kia đã nhận.

Nagle và độ trễ trên mạng

TCP có bộ đệm riêng của nó: thuật toán Nagle gom các mẩu nhỏ lại chờ gửi chung, để tránh gửi gói 41 byte chỉ chứa 1 byte dữ liệu. Tốt cho thông lượng, tệ cho độ trễ — game hoặc terminal tương tác sẽ thấy khựng ~40 ms.

Đây cũng là một nguyên nhân của hiện tượng gộp thông điệp ở I2.

Bẫy. Trộn fread (có đệm libc) với read (thẳng xuống nhân) trên cùng một fd thì dữ liệu lẫn lộn, vì stdio đã đọc trước một khối vào đệm riêng. Chọn một tầng và ở nguyên đó.

J2 Bộ đệm vòng 3 giờ›

Mục tiêu. Cài được cấu trúc dữ liệu mà mọi server không chặn đều cần: chỗ chứa byte đã tới nhưng chưa xử lý xong.

Vì sao cần

Ở J4 bạn sẽ đọc dữ liệu tới từng mẩu, không đủ một thông điệp. Phải cất đi, chờ mẩu sau. Bộ đệm tự lớn ở C4 làm được nhưng phải dịch chuyển dữ liệu mỗi lần tiêu thụ (tốn O(n)). Bộ đệm vòng làm mọi thao tác trong O(1) và không cấp phát thêm lần nào.

#include <stdint.h>
#include <string.h>

struct vong {
    uint8_t *buf;
    size_t   co;      // dung lượng, nên là lũy thừa của 2
    size_t   dau;     // vị trí đọc
    size_t   duoi;    // vị trí ghi
    size_t   dang_co; // số byte đang chứa -- giải quyết mập mờ đầy/rỗng
};

size_t con_trong(const struct vong *v) { return v->co - v->dang_co; }

size_t ghi(struct vong *v, const uint8_t *src, size_t n)
{
    if (n > con_trong(v)) n = con_trong(v);   // ghi được bao nhiêu hay bấy nhiêu

    // có thể phải chia hai đoạn vì dữ liệu quấn qua mép mảng
    size_t doan1 = v->co - v->duoi;
    if (doan1 > n) doan1 = n;

    memcpy(v->buf + v->duoi, src, doan1);
    memcpy(v->buf, src + doan1, n - doan1);   // n-doan1 = 0 thì memcpy vô hại

    v->duoi = (v->duoi + n) % v->co;
    v->dang_co += n;
    return n;
}

size_t doc(struct vong *v, uint8_t *ra, size_t n)
{
    if (n > v->dang_co) n = v->dang_co;

    size_t doan1 = v->co - v->dau;
    if (doan1 > n) doan1 = n;

    memcpy(ra, v->buf + v->dau, doan1);
    memcpy(ra + doan1, v->buf, n - doan1);

    v->dau = (v->dau + n) % v->co;
    v->dang_co -= n;
    return n;
}
Chỗ mập mờ kinh điển

Nếu chỉ có dau và duoi, thì dau == duoi vừa có nghĩa rỗng vừa có nghĩa đầy. Hai cách gỡ:

  • Giữ thêm biến dang_co (cách trên) — rõ ràng, dễ đọc.
  • Chừa một ô không dùng, coi đầy là (duoi+1)%co == dau — tiết kiệm một biến, hay gặp trong code nhúng.
Mẹo lũy thừa của 2

Nếu co là lũy thừa của 2 thì % co đổi được thành & (co - 1) — nhớ E1. Phép AND nhanh hơn phép chia khoảng 20 lần, và trên đường dữ liệu nóng của server thì điều đó đo được.

Nó ở đâu trong đời thật
  • Đệm nhận/gửi của socket trong nhân Linux chính là bộ đệm vòng.
  • Hàng đợi gói của card mạng (ring descriptor) — cùng cấu trúc, do phần cứng và driver dùng chung.
  • Đệm âm thanh, đệm log, hàng đợi một-nhà-sản-xuất-một-người-tiêu-thụ giữa hai luồng (H4) — bản không khóa của nó là nền của mọi thư viện hiệu năng cao.
Bẫy. Bản dùng cho hai luồng không chỉ cần đổi volatile. Cần atomic và rào cản bộ nhớ, vì CPU có thể sắp xếp lại thứ tự ghi. Đây đúng là điểm ở phần bẫy của H4 — đọc lại trước khi làm bài 3.
Bài tập
  1. Cài đủ cấu trúc trên. Kiểm: ghi 10, đọc 5, ghi 8, đọc 12 — với dung lượng 16. In dau, duoi, dang_co sau mỗi bước. Gọi hàm trước, in sau — đừng viết printf("%zu %zu", ghi(&v,...), v.dau): chuẩn C không quy định thứ tự đánh giá tham số, nên bạn có thể in ra giá trị trước khi ghi và tưởng code sai.
  2. Đổi % thành &, thêm kiểm tra dung lượng là lũy thừa của 2 bằng assert((co & (co-1)) == 0) (nhớ E6). Đo 10 triệu thao tác cả hai bản.
  3. Ghép J2 với I2: dùng bộ đệm vòng làm chỗ chứa, viết hàm int lay_ban_tin(struct vong *v, uint8_t *ra) trả về 1 khi trong đệm đã đủ một thông điệp có tiền tố độ dài, 0 khi chưa đủ. Đây chính là lõi của J3.

J3 Máy trạng thái — phân tích dữ liệu tới từng mẩu 4 giờ›

Mục tiêu. Viết bộ phân tích HTTP chạy đúng dù dữ liệu tới từng byte một. Đây là kỹ thuật phân biệt code đồ chơi với code thật.

Vấn đề

Ở I4 bạn đọc cả yêu cầu vào một bộ đệm rồi mới sscanf. Cách đó chỉ chạy khi bạn được phép chặn tới lúc đủ dữ liệu. Server không chặn (J4) không có quyền đó: read() trả về 3 byte rồi thôi, bạn phải quay ra phục vụ client khác và nhớ mình đang phân tích dở tới đâu.

Chỗ "nhớ đang dở tới đâu" chính là trạng thái.

Máy trạng thái phân tích thông điệp có tiền tố độ dài
enum trang_thai { CHO_DO_DAI, CHO_THAN, XONG };

struct bo_phan_tich {
    enum trang_thai tt;
    uint8_t  dem_dai[4];
    size_t   da_doc_dai;      // 0..4
    uint32_t do_dai;
    uint8_t *than;
    size_t   da_doc_than;
};

// Nạp thêm n byte. Trả về số thông điệp hoàn chỉnh vừa hoàn thành.
// Hàm này KHÔNG BAO GIỜ chặn, không bao giờ gọi read.
int nap(struct bo_phan_tich *p, const uint8_t *vao, size_t n)
{
    int xong = 0;
    size_t i = 0;

    while (i < n) {
        switch (p->tt) {

        case CHO_DO_DAI: {
            size_t can = 4 - p->da_doc_dai;
            size_t lay = (n - i < can) ? n - i : can;
            memcpy(p->dem_dai + p->da_doc_dai, vao + i, lay);
            p->da_doc_dai += lay;  i += lay;

            if (p->da_doc_dai == 4) {
                uint32_t d;  memcpy(&d, p->dem_dai, 4);
                p->do_dai = ntohl(d);
                if (p->do_dai > 1024*1024) return -1;   // chặn gói bậy, nhớ I2
                p->than = malloc(p->do_dai);
                if (!p->than) return -1;
                p->da_doc_than = 0;
                p->tt = CHO_THAN;
            }
            break;
        }

        case CHO_THAN: {
            size_t can = p->do_dai - p->da_doc_than;
            size_t lay = (n - i < can) ? n - i : can;
            memcpy(p->than + p->da_doc_than, vao + i, lay);
            p->da_doc_than += lay;  i += lay;

            if (p->da_doc_than == p->do_dai) {
                xu_ly_ban_tin(p->than, p->do_dai);
                free(p->than);  p->than = NULL;
                p->da_doc_dai = 0;
                p->tt = CHO_DO_DAI;      // sẵn sàng cho thông điệp kế
                xong++;
            }
            break;
        }

        default: return -1;
        }
    }
    return xong;
}
Ba tính chất khiến nó đúng
  1. Không bao giờ giả định n đủ lớn — mọi bước đều lấy min(còn cần, còn có).
  2. Toàn bộ tiến độ nằm trong struct, không nằm trong biến cục bộ. Nên gọi lại bao nhiêu lần cũng được.
  3. Một lần nap() có thể hoàn thành nhiều thông điệp — vòng while lo việc đó. Quên vòng này là bỏ sót thông điệp thứ hai trong cùng một gói.
Áp cho HTTP

Trạng thái: DONG_YEU_CAU → CAC_HEADER → THAN → XONG. Chuyển từ header sang thân khi gặp dòng trống; độ dài thân lấy từ Content-Length. Đây đúng là cách nginx và Node.js phân tích HTTP.

Bẫy. Máy trạng thái viết bằng nhiều biến cờ rời rạc (bool da_co_header; bool dang_doc_than;) sẽ sinh ra tổ hợp trạng thái vô nghĩa và lỗi không tài nào tìm ra. Dùng một enum — một biến, mỗi lúc một giá trị, liệt kê được hết.
Bài tập
  1. Cài nap(). Kiểm bằng cách đưa vào từng byte một (nap(p, &b, 1) trong vòng lặp). Phải ra kết quả y hệt khi đưa cả khối. Đây là phép thử quyết định.
  2. Đưa vào một mảng chứa hai thông điệp rưỡi. Kiểm rằng nó báo 2 và giữ đúng trạng thái dở cho thông điệp thứ ba.
  3. Viết máy trạng thái HTTP với 4 trạng thái ở trên. Kiểm bằng cách gửi yêu cầu chia làm 3 lần bằng printf ... | nc -q1 có sleep ở giữa.

Sau đó read() trên socket chưa có dữ liệu không chặn nữa — nó trả về ngay -1 với errno == EAGAIN (bằng EWOULDBLOCK). Đây không phải lỗi, mà là câu trả lời "chưa có gì". Xử lý sai chỗ này là nguồn lỗi phổ biến nhất khi mới chuyển sang không chặn.

Nhưng không chặn một mình thì vô dụng

Nếu chỉ hỏi vòng quanh 10 000 fd xem cái nào có dữ liệu, bạn đốt 100% CPU để hầu hết lần hỏi đều nhận EAGAIN. Cần một cách ngủ cho tới khi có ít nhất một fd sẵn sàng — đó là việc của select/poll/epoll.

Tương đương của epoll: kqueue trên BSD/macOS, IOCP trên Windows. Học epoll rồi thì hiểu cả ba, vì ý tưởng giống nhau.

Vòng lặp sự kiện bằng epoll
#include <sys/epoll.h>

int ep = epoll_create1(0);

struct epoll_event ev = { .events = EPOLLIN, .data.fd = fd_nghe };
epoll_ctl(ep, EPOLL_CTL_ADD, fd_nghe, &ev);

struct epoll_event sk[64];

while (1) {
    int n = epoll_wait(ep, sk, 64, -1);      // -1 = ngủ vô hạn, KHÔNG tốn CPU
    if (n < 0) { if (errno == EINTR) continue; break; }   // nhớ H3

    for (int i = 0; i < n; i++) {
        int fd = sk[i].data.fd;

        if (fd == fd_nghe) {
            // vòng while: có thể nhiều client tới cùng lúc
            int c;
            while ((c = accept(fd_nghe, NULL, NULL)) >= 0) {
                dat_khong_chan(c);
                struct epoll_event e = { .events = EPOLLIN, .data.fd = c };
                epoll_ctl(ep, EPOLL_CTL_ADD, c, &e);
            }
            // thoát vòng khi accept trả EAGAIN -- hết client đang chờ

        } else {
            char buf[4096];
            ssize_t r = read(fd, buf, sizeof buf);

            if (r > 0) {
                nap(&bo_phan_tich[fd], (uint8_t *)buf, r);   // J3
            } else if (r == 0) {
                // client đóng kết nối một cách sạch sẽ
                epoll_ctl(ep, EPOLL_CTL_DEL, fd, NULL);
                close(fd);
            } else if (errno != EAGAIN && errno != EINTR) {
                epoll_ctl(ep, EPOLL_CTL_DEL, fd, NULL);
                close(fd);
            }
        }
    }
}
Toàn bộ giai đoạn J tụ về đây
  • Không được chặn → phải phân tích từng mẩu → J3.
  • Dữ liệu dở phải cất → J2.
  • Mỗi fd cần một struct trạng thái riêng → mảng chỉ số theo fd, và mảng nhanh hơn danh sách liên kết vì cache → G4.
  • Ghi cũng có thể chặn: write() trả về ít hơn bạn xin khi đệm gửi đầy. Phải cất phần còn lại và đăng ký EPOLLOUT. Đây là nửa mà người mới hay quên.
Mức kích hoạt và mức thay đổi

Level-triggered (mặc định): còn dữ liệu chưa đọc thì epoll_wait còn báo. Dễ đúng. Edge-triggered (EPOLLET): chỉ báo một lần khi có dữ liệu mới. Nhanh hơn, nhưng bắt buộc phải read trong vòng lặp cho tới EAGAIN, nếu không dữ liệu còn lại nằm im vĩnh viễn và kết nối treo. Người mới nên dùng level-triggered.

Bẫy. Quên dat_khong_chan() cho fd của client. Server chạy đúng khi thử một client, rồi treo cả hệ thống khi một client gửi nửa thông điệp rồi im — vì read() chặn, và cả vòng lặp sự kiện đứng lại, kéo theo 9999 client kia. Không chặn là bắt buộc, không phải tùy chọn.
