Một file, 60 dòng · Phase 1 · tuần 1

Câu hỏi: Cơ sở dữ liệu ít nhất phải làm được gì?  Trả lời: Ghi được, đọc lại được. Hết.

// PUT: nối vào cuối file. Không bao giờ sửa thứ đã ghi.
void put(const char *key, const char *val) {
    FILE *f = fopen("data.db", "a");        // "a" = append
    fprintf(f, "%s\t%s\n", key, val);
    fclose(f);
}

// GET: quét cả file từ đầu, nhớ giá trị CUỐI CÙNG khớp key.
int get(const char *key, char *out) {
    FILE *f = fopen("data.db", "r");
    if (!f) return -1;
    char line[1024];
    int found = -1;
    while (fgets(line, sizeof line, f)) {
        char *tab = strchr(line, '\t');
        if (!tab) continue;
        *tab = '\0';                         // cắt đôi: trước tab là key
        if (strcmp(line, key) == 0) {
            char *v = tab + 1;
            v[strcspn(v, "\n")] = '\0';
            strcpy(out, v);
            found = 0;                       // bản ghi sau đè bản ghi trước
        }
    }
    fclose(f);
    return found;
}

Đó là một cơ sở dữ liệu thật. Nó có hai tính chất mà các engine thật cũng có:

  • Append-only — chỉ nối thêm, không sửa chỗ cũ. Ghi tuần tự nhanh hơn ghi ngẫu nhiên rất nhiều.
  • Last write wins — sửa thì ghi đè bản mới ở cuối; xoá thì ghi một “bia mộ” (tombstone).

Cả LSM Tree của RocksDB lẫn WAL của PostgreSQL đều đứng trên đúng hai ý này.

Trang có cấu trúc · Phase 1 · tuần 1–2

Câu hỏi: File dạng dòng text thì lôi thôi — muốn nhảy tới bản ghi thứ 500 thì sao?  Ý tưởng: Chia file thành trang (page) cố định 4KB, mỗi trang tự mô tả nội dung của nó.

Vì sao 4KB: vì đó là kích thước page của kernel Linux và thường là kích thước khối của hệ tệp. Ghi đúng một page = kernel làm đúng một thao tác. Ghi 4KB+1 byte = kernel phải đụng hai page. Đây là ví dụ đầu tiên về việc kiến trúc máy tính rò rỉ lên tận thiết kế phần mềm — thứ CSAPP dạy suốt.

checksum trong header để phát hiện torn page: máy chết giữa lúc ghi, nửa trang mới nửa trang cũ. Không có checksum thì bạn đọc phải rác mà không biết.

B-Tree · Phase 1 · tuần 3–5

Câu hỏi: Bảng băm trong RAM không chứa nổi 1 tỷ key. Và tôi muốn hỏi “cho tôi mọi key từ user:100 đến user:200” — bảng băm chịu.  Ý tưởng: Cây giữ key có thứ tự, và cây nằm trên đĩa.

Điểm mấu chốt sách hay nói lướt: mỗi node là đúng một page 4KB. Vì đọc đĩa tính theo page. Một page chứa ~200 key. Cây 3 tầng chứa 200³ = 8 triệu key và tìm bất kỳ key nào chỉ tốn 3 lần đọc đĩa. Cây 4 tầng: 1,6 tỷ key, 4 lần đọc đĩa.

Đó là toàn bộ lý do B-Tree thống trị cơ sở dữ liệu suốt 50 năm. Nó tối ưu cho thứ đắt nhất: số lần chạm đĩa, không phải số phép so sánh.

Lớp kiến thức nằm giữa “khái niệm” và “gõ được code” — thứ không ai dạy vì ai cũng tưởng bạn biết rồi.

1. Syscall thật ra là gì

write(fd, "hello", 5) trông như gọi hàm thường, nhưng nó không phải. Nó chạy lệnh máy syscall, CPU chuyển từ user mode sang kernel mode, kernel làm việc, rồi quay về.

Đó là lý do tồn tại của đệm I/O, buffer pool, group commit.

Mẹo đọc sách cơ sở dữ liệu

Mỗi khi thấy một kỹ thuật tối ưu, hỏi: “nó đang tránh syscall nào?” Chín trên mười lần, đó là câu trả lời.

2. File descriptor chỉ là một số nguyên

open() trả về 3. Con số đó không là địa chỉ, không là handle bí ẩn. Nó là chỉ số trong một mảng mà kernel giữ riêng cho tiến trình của bạn.

Ở Phase 3 bạn giữ 10.000 fd cùng lúc. Biết nó chỉ là mảng thì epoll hết bí ẩn — bạn đang đưa cho kernel một danh sách chỉ số và bảo “cái nào sẵn sàng thì gọi tôi”. Và trong Linux mọi thứ đều là file: file thật, socket, pipe, thiết bị, thậm chí cgroup.

3. write() KHÔNG ghi xuống đĩa

Sự thật quan trọng nhất mục này

fsync(fd) = “ghi xuống đĩa thật, đừng trả về cho tới khi xong”. Toàn bộ chương WAL, toàn bộ khái niệm độ bền đều sinh ra từ sự thật này.

4. Trên đĩa không có “sửa”, chỉ có “ghi đè cả khối”

Đĩa không cho bạn sửa 1 byte. Đơn vị nhỏ nhất là một sector (512B hoặc 4KB). Sửa 1 byte = đọc cả khối vào RAM, sửa, ghi cả khối xuống. Nếu cấu trúc dữ liệu không thẳng hàng với biên page, mỗi lần ghi nhỏ biến thành hai lần đọc-sửa-ghi.

7. Runtime là gì

C: main() nói chuyện thẳng với kernel. Go: trước main(), runtime khởi động — GC, scheduler, netpoller. Cái giá: mất quyền kiểm soát chi tiết, GC có thể gây khựng. Cái được: 1.500 dòng Go làm bằng 2.500 dòng C, ít bug hơn nhiều.

C ở tầng dưới nơi cần kiểm soát từng byte. Go ở tầng trên nơi cần đi nhanh và an toàn. Đúng như ngành công nghiệp thật làm.

3. Viết util.c · 2 giờ

File này theo bạn suốt hai năm. Nó giải quyết một vấn đề C không lo hộ: mọi syscall đều có thể lỗi, và bạn phải xử lý.

// Đọc cho ĐỦ n byte. read() có thể trả về ít hơn yêu cầu — đó
// không phải lỗi, đó là bình thường. Phải gọi lại cho tới khi đủ.
ssize_t read_full(int fd, void *buf, size_t n);

// Ghi cho ĐỦ n byte. write() cũng vậy.
ssize_t write_full(int fd, const void *buf, size_t n);

Ba thứ phải xử lý đúng, không bỏ qua cái nào:

  • Trả về ít hơn yêu cầu → gọi lại phần còn thiếu
  • Trả về -1 với errno == EINTR → bị signal ngắt, thử lại, không phải lỗi
  • Trả về 0 khi đọc → hết file / đầu kia đóng kết nối

4. Đọc CSAPP Ch1 · 1 giờ

Đọc như xem bản đồ trước chuyến đi. Không sa đà, không làm bài tập.

Nghi thức hàng tuần

Mỗi buổi học — 5 phút đầu: mở tab này xem còn gì chưa tick · mở tab Sách xác nhận đọc chương nào.

Cuối mỗi buổi — 5 phút cuối: tick những gì thật sự xong · commit dù chỉ 20 dòng · chỗ bí quá 2 tiếng thì ghi lại.

Chủ nhật — 20 phút: đọc lại Sáu luật đi đường. Trượt tiến độ 2 tuần liên tiếp → dừng lại, xem lại nhịp 15–20h có thực tế không. Điều chỉnh kế hoạch chứ đừng điều chỉnh sự thật.

Câu hỏi tự kiểm mỗi cuối tuần

  1. Tuần này tôi thêm năng lực gì mà hệ thống tuần trước không có?
  2. Nó giải bài toán nào mà tôi tự cảm nhận được, không phải sách bảo có?
  3. Tôi giải thích được cho người khác trong 2 phút không?

Nếu câu 2 trả lời không được — bạn đang code theo sách chứ không theo nhu cầu. Dừng lại, lùi một bước, đo lại hệ thống hiện tại để tìm ra chỗ đau thật.
